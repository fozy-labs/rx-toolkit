# Валидация и запросы

Валидация непрерывна: `issues$` каждого узла — вычисляемый сигнал, ничего не «запускается». Схема, правила, запросы и сервер дают issue; политика `showErrors` решает только, какие из них видны.

## Issue

```typescript
type Issue = {
    path: ReadonlyArray<string | number>; // абсолютный от корня, строки списка — по индексу
    message: string;
    severity: "error" | "warning";
    source: IssueSource;
    code?: string;
};
```

| `source` | Откуда | Строка источника (для логов) |
|---|---|---|
| `{ type: "schema" }` | схема поля | `schema` |
| `{ type: "rule", path, name }` | правило `validate` | `services.freeTariff` |
| `{ type: "callback", path, name }` | упавший колбэк: `computed`, ключ запроса, `disabled`, хендлер `submit` | `services.computed.total` |
| `{ type: "server" }` | ответ сабмита, см. [Серверные ошибки](submit.md#серверные-ошибки) | `server` |

- **`path` / `name` источника.** Короткая форма `validate` называется именем узла (на корне — `name` формы) под путём родителя; запись правил — ключом правила под путём узла.
- **`severity: "warning"`** не влияет на `isValid$` и на сабмит.
- **`code`** для i18n и аналитики передаётся третьим аргументом: `error(node, message, { code })`. Из схемы и с сервера приходит как есть.
- **`path`** issue схемы и правил вычисляется из текущей позиции узла, поэтому после `move` строки он актуален. Серверный `path` остаётся таким, каким его прислал сервер.
- **Порядок** в агрегатах — порядок дерева: сначала собственные issue узла (у поля: схема → правила → упавшие ключи запросов → сервер), затем дети в порядке определения, затем строки списка в порядке `items$`.

Сигналы узла: `issues$` — все, `errors$` / `warnings$` — по severity, `visibleErrors$` / `visibleWarnings$` — видимые по политике. У группы и списка `ownIssues$` — issue самого узла без детей.


## Правила

`validate` — функция (короткая форма) или запись именованных правил. Каждое правило — отдельное вычисление, которое пересчитывается только от того, что прочитало.

```typescript
validate: {
    freeTariff: ({ fields, error }) => { /* … */ },
    corporate: ({ fields, warn }) => { /* … */ },
},
```

- **`error` / `warn`** собирают issue текущего прогона; куда они адресуются — в [Что видит колбэк](definition.md#что-видит-колбэк).
- **Правила только читают.** Писать в форму из правила нельзя: производное значение, записанное через `set`, затирало бы данные из `initialize`. Такие преобразования делает обработчик события в UI.
- **Гейт по разобранности — `parsed$().isParsed`, не `isValid$`.** `isValid$` включает правило, которое его читает, — это цикл (и в контексте его нет).


## Видимость ошибок

Ошибки вычисляются всегда; `showErrors` фильтрует `visibleErrors$` и `visibleWarnings$`.

| `showErrors` | Видны после |
|---|---|
| `"touched"` (по умолчанию) | `blur()` или `markTouched()` |
| `"modified"` | первой правки (`set()` создал черновик) |
| `"submitted"` | сабмита формы |
| `"always"` | сразу |

- **Сабмит показывает всё.** `submit()` помечает все узлы `touched` и `submitted`; после него ошибки видны под любой политикой. `reset()` и `initialize()` снимают `submitted` так же, как `touched`.
- **Политика наследуется**: узел без своей `showErrors` берёт её у родителя. Issue фильтруется по политике узла, которому принадлежит; `visibleErrors$` группы — видимые ошибки детей плюс её собственные по её политике.
- **Issue группы без узла** (`error("…")` в правиле группы) подчиняется агрегатам группы: `touched` — когда тронут хотя бы один её узел, `modified` — когда изменён.


## Условные поля: disabled

```typescript
const Payer = g({
    fields: { kind, inn },
    disabled: { inn: ({ fields }) => fields.kind.value$() !== "company" },
});
```

- Отключённый узел исключён из `value$` / `parsed$` родителя (ключа нет), его issue не агрегируются, а `isValid$`, `isDirty$`, `isModified$`, `isTouched$` и `isPending$` родителя его не учитывают.
- `isDisabled$` наследуется вниз: у детей отключённой группы он тоже `true`.
- Черновик отключённого поля сохраняется и снова виден после включения. `reset`, `initialize` и `markTouched` доходят и до отключённых узлов.
- Запросы отключённого узла продолжают работать, пока их кто-то читает.
- **Цена в типах:** ключи из `disabled` необязательны в `value$`, `parsed$` и выходе группы, в том числе в `parsed$` сабмита. Собственный `value$` поля остаётся обязательным.
- `disabled` задаётся только для прямых детей группы; у списка его нет.


## Запросы

Запрос — асинхронные данные для правил и UI: ресурс query, аргументы которого вычисляет ключ.

```typescript
queries: {
    emailInfo: ({ parsed$ }) => {
        const parsed = parsed$();
        return parsed.isParsed && getEmailInfo.bind(parsed.value);
    },
    cities: { bind: ({ value$ }) => getCities.bind(value$()), debounce: 300 },
},
```

- **Ключ** возвращает `resource.bind(args)`, falsy-значение или `SKIP` — тогда запрос простаивает (`idle`). Ключ всегда связывает один и тот же ресурс; другой ресурс — `FormConfigError`.
- **`{ bind, debounce }`** откладывает смену аргументов на `debounce` мс.

### Узел запроса

В инстансе каждый ключ `queries` становится узлом `queries.<k>`, алиас `queries.<k>$ === queries.<k>.state$`:

| Член | Что это |
|---|---|
| `state$` | состояние [сцепления ресурса](../query/api/resource-clutch.md#состояние-tresourceclutchstate) как есть (`status`, `dataSource`, `data`, …); до первого ключа с аргументами — замороженное `idle`, методы которого ничего не делают |
| `isDebouncing$` | у ключа новые аргументы, которые ещё не дошли до сцепления |
| `whenSettled(options?)` | промис: есть что отрисовать — по [правилу `whenSettled` сцепления](../query/api/resource-clutch.md#whensettled); с `{ waitForDone: true }` — узел не в ожидании |

`whenSettled()` без опций на простаивающем запросе (`SKIP`) не резолвится никогда; `{ waitForDone: true }` считает `idle` завершённым сразу.

`isPending$` узла-владельца (и всех его предков) истинен, пока любой его запрос в полёте или в debounce.

### Активность

Запрос активен, пока у него есть потребитель, и ничего не делает без него:

- **Потребитель** — подписка на `state$` или на сигнал, который его читает: правило, `isPending$`, `issues$`, снимок `state$` поля. Отрисованное поле держит свои запросы горячими.
- **Холодное чтение запускает запрос.** `form.isValid$.peek()` без подписки активирует узлы, запрос уходит, чтение возвращает pending. Узел держится до конца микротаска, поэтому два чтения подряд дают один объект.
- **Деактивация — `switch(SKIP)`.** Холодный узел не хранит аргументов; повторная активация сразу применяет текущие аргументы и берёт запись из кэша, пока та в retention. SWR-fallback прошлых аргументов (`dataSource: "previous"`) есть только внутри одного горячего периода.

### Debounce

- Первое значение после активации применяется сразу; debounce задерживает только изменения.
- Falsy-ключ применяется сразу и отменяет таймер.
- Возврат к уже применённым аргументам отменяет таймер без запроса.
- Остальные изменения ждут `debounce` мс, каждое новое перезапускает таймер; программные `set()` тоже. Досрочно таймер не сбрасывается.


## Проверка email

Правило, которое читает запрос, видит чужие данные двумя путями:

| Путь | Признак |
|---|---|
| debounce: аргументы новые, сцепление ещё на старых | `queries.<k>.isDebouncing$()` |
| сцепление на новых аргументах, но показывает данные прошлых (SWR), `placeholderData` или прошлые данные при ошибке новых | `dataSource !== "current"` |

Правило проверяет оба признака и обрабатывает ошибку запроса явно — иначе после ожидания сабмита упавшая проверка выглядит как «проблем нет»:

```typescript
const email = f({
    schema: z.email().trim(),
    defaultValue: "",
    queries: {
        emailInfo: {
            bind: ({ parsed$ }) => {
                const parsed = parsed$();
                return parsed.isParsed && getEmailInfo.bind(parsed.value);
            },
            debounce: 300,
        },
    },
    validate: ({ queries, error, warn }) => {
        if (queries.emailInfo.isDebouncing$()) return;
        const info = queries.emailInfo$();
        if (info.status === "error") return warn("Не удалось проверить email");
        if (info.dataSource !== "current") return;
        if (!info.data.isValid) error("Email занят");
        if (info.data.isCorporate) warn("Корпоративный адрес");
    },
});
```


## Броски в колбэках

Ни один реактивный колбэк не выбрасывает исключение из графа формы:

| Колбэк | Исход броска |
|---|---|
| схема бросила | error-issue с источником `schema` |
| схема вернула промис | error-issue `schema` и один `console.error` с подсказкой перенести проверку в `queries` + `validate` |
| правило | одна error-issue с источником правила; issue этого прогона отбрасываются |
| ключ запроса | запрос простаивает, как при `SKIP`; error-issue `callback` на узле-владельце |
| `disabled` | узел не отключён; error-issue `callback` |
| `computed` | сигнал держит последнее удачное значение (до первого — `undefined`) и не бросает при чтении; error-issue `callback` в `ownIssues$` группы |
| `equals` | `console.error`, решает `Object.is` |
| хендлер `submit` | `submit()` резолвится `false`, `status$` — `"error"`, корневая issue `callback` до следующей попытки |
| `mapSubmitError` | `console.error`, issue строит встроенный маппер |


## Ошибки конфигурации

`FormConfigError` — ошибка в самой форме, а не в данных. Поля `path` (путь опции: `"fields.email$"`, `"services.validate.freeTariff"`) и `detail`.

- **При создании определения:** неизвестная опция, неверное имя, корневая опция у вложенной группы, ключ `disabled`, которого нет среди детей, и т. п.
- **Во время вычисления:** цикл (колбэк прочитал сигнал, зависящий от его результата), `error(node)` вне поддерева правила, второй ресурс на ключе запроса. Ошибка становится состоянием вычисления: чтение бросает её, подписчики получают её в `error`, пока не изменится зависимость.
- **Цикл через приведение типов или замыкание.** Контексты не дают прочитать вердикт, но `as` или замыкание на сигнал инстанса (`form.isValid$`) обходят типы. Такой цикл обнаруживается и в подписанной форме: любой читатель получает `FormConfigError`. Не читайте вердикты формы из её колбэков.
- **Сабмит:** `submit` вернул не `command.bind(args)` и не промис, или промис разрешился в `bind` команды — `submit()` отклоняется с `FormConfigError`.


## Рецепты

### Фокус на первой ошибке

`visibleErrors$` корня упорядочен по дереву, поэтому первая видимая ошибка — самое верхнее поле. Если `name` инпутов совпадает с путём (`phones.1.number`):

```typescript
async function submitAndFocus(form: FormInstance<typeof RegistrationForm>) {
    if (await form.submit()) return;
    const first = form.visibleErrors$.peek()[0];
    if (first) document.querySelector<HTMLElement>(`[name="${first.path.join(".")}"]`)?.focus();
}
```

Путь серверной issue — такой, каким его прислал сервер; если он не совпадает со структурой формы, ищите элемент по своим правилам.

### Проверка шага визарда

Отдельного API нет: `markTouched()` шага → дождаться `!isPending$` → `isValid$`.

```typescript
import { filter, firstValueFrom } from "rxjs";

async function isStepValid(step: GroupNode): Promise<boolean> {
    step.markTouched();
    const hold = step.isValid$.obs.subscribe(); // держит запросы шага горячими
    try {
        await firstValueFrom(step.isPending$.obs.pipe(filter((isPending) => !isPending)));
        return step.isValid$.peek();
    } finally {
        hold.unsubscribe();
    }
}

const ok = await isStepValid(form.fields.account);
```

- Работает под `showErrors` `"touched"` и `"always"`: `"submitted"` открывается только сабмитом формы.
- Ждёт только запросы шага: запросы, объявленные на предках, рецепт не ждёт.
