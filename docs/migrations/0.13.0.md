# Миграция с версии 0.12.x на 0.13.0

Релиз меняет в модуле Query две вещи сразу.

- **Словарь.** «Агент» стал «сцеплением» (`Clutch`), `refresh` — `invalidate`, `pack` — `bind`,
  ключ записи у команды — `entryKey`. Чистые переименования прикрыты `@deprecated`-алиасами:
  код компилируется как есть и работает один релиз, [до 0.14.0](#deprecated-удаляется-в-0140).
- **Форма реактивного состояния.** Состояние сцепления ресурса стало матрицей
  `status` × `dataSource`, у команды и у бесконечной ленты поменялся набор флагов.
  Здесь алиасов нет: удалённые поля компилятор покажет поимённо.

Опасны не они, а места, где код продолжает компилироваться, а ведёт себя иначе. Их четыре,
все разобраны ниже: [`status === 'error'` стал шире](#статус-error-стал-шире),
[`switch (status)` перестал быть разбиением](#switch-status-больше-не-разбиение),
[`entryKey` в дескрипторе команды](#key--entrykey) и
[`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи).

## Порядок миграции

1. Обновиться и собрать проект. Всё, что компилятор покажет сразу, — это форма состояния
   и переименования машины; алиасы остальное скрывают.
2. Пройти [таблицу флагов](#флаги-что-чем-заменить) и заменить чтения состояния.
3. Перечитать четыре места, на которые компилятор не укажет (или укажет не везде):
   [`status === 'error'`](#статус-error-стал-шире),
   [`switch (status)`](#switch-status-больше-не-разбиение),
   [`entryKey` в дескрипторе](#key--entrykey),
   [`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи).
4. Переименовать словарь по [таблицам](#словарь) — алиасы дают на это время до 0.14.0,
   но чем раньше, тем меньше смешанной терминологии в коде.


## Словарь

### Agent → Clutch

Термин `Agent` обещал автономию, которой у объекта нет, и конфликтовал с ИИ-агентами.
Сцепление (clutch) соединяет потребителя с записью кэша и переключает записи, не останавливая
ресурс, — [метафора разобрана в концепции](../query/concepts/clutch.md).

| Было (0.12.x) | Стало (0.13.0) |
|---|---|
| `ResourceAgent`, `CommandAgent` | `ResourceClutch`, `CommandClutch` |
| `IResourceAgent`, `ICommandAgent` | `IResourceClutch`, `ICommandClutch` |
| `TResourceAgentState` + варианты | `TResourceClutchState` + варианты |
| `TCommandAgentState` + варианты | `TCommandClutchState` + варианты |
| `TAgentStatus` | `TClutchStatus` |
| `resource.createAgent()` | `resource.createClutch()` |
| `command.createAgent(key?)` | `command.createClutch(entryKey?)` |

```typescript
// Было
const agent = usersResource.createAgent();

// Стало
const clutch = usersResource.createClutch();
```

`TAgentStatus` остаётся алиасом, но **набор значений сузился**: было
`'idle' | 'pending' | 'success' | 'error' | 'refreshing' | 'refresh-error'`, стало четыре
значения `TClutchStatus`. Код, перечисляющий статусы вручную, алиас не спасёт — см.
[Статус error стал шире](#статус-error-стал-шире).

### refresh → invalidate

Один корень на «пометить устаревшим и перезапросить в фоне» на всех уровнях.

| Уровень | Было | Стало |
|---|---|---|
| `Resource` | `refresh(args)` | `invalidate(args)` |
| Запись кэша | `entry.refresh()` | `entry.invalidate()` |
| Сцепление ресурса | `clutch.refresh()` | `clutch.invalidate()` |
| Состояние сцепления | `state.refresh()` | `state.invalidate()` |
| `useInfiniteResource` | `feed.refresh()` | `feed.invalidate()` |

```typescript
// Было
usersResource.refresh({ page: 1 });

// Стало
usersResource.invalidate({ page: 1 });
```

Семантика вызова не изменилась ни на одном уровне, кроме одного случая —
[`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи).

**Машина — без алиасов.** `Machine*` экспортируется публично; у неё меняется форма состояния,
поэтому слоя совместимости нет и `@deprecated`-пометок тоже:

| Было | Стало |
|---|---|
| статусы `'refreshing'`, `'refresh-error'` | `'invalidating'`, `'invalidate-error'` |
| классы `MachineRefreshing`, `MachineRefreshError` | `MachineInvalidating`, `MachineInvalidateError` |
| типы `TRefreshingState`, `TRefreshErrorState` | `TInvalidatingState`, `TInvalidateErrorState` |
| `machine.refresh()` | `machine.invalidate()` |

```typescript
// Было
if (entry.machine$().status === 'refresh-error') { /* … */ }

// Стало
if (entry.machine$().status === 'invalidate-error') { /* … */ }
```

Из `TPendingState` и `TInvalidatingState` убрано поле `isRetrying`: повтор в полёте — это
`error !== null`. Статусы `invalidating` / `invalidate-error` в **машине** остались; из
состояния сцепления и записи они ушли, см. [матрицу](../query/api/resource-clutch.md#варианты-состояния).

### key → entryKey

Начните с этого пункта: **дескриптор команды — единственное переименование, от которого алиас
не защищает.** У `TBoundCommand` поле `key` стало `entryKey`, а `@deprecated`-алиас
`TPackedCommand` указывает на новый тип и старое поле не сохраняет.

```typescript
// Было
const { key } = addTodoCommand.pack({ text: 'Задача' }, 'my-key');

// Стало
const { entryKey } = addTodoCommand.bind({ text: 'Задача' }, 'my-key');
```

В типизированном коде компилятор укажет на деструктуризацию (`Property 'key' does not exist`).
Но там, где дескриптор проходит через нетипизированную границу — JS, `any`, собственный реестр
или транспорт, — чтение `.key` молча даёт `undefined`, и команда запускается со сгенерированным
ключом вместо общего. Найдите чтения поля грепом.

У команды под словом `key` жили две разные вещи. Переименовывается только ключ записи кэша:

| Было | Стало |
|---|---|
| `command.execute(args, key?)` | `command.execute(args, entryKey?)` |
| `command.createAgent(key?)` | `command.createClutch(entryKey?)` |
| `command.pack(args, key?)` | `command.bind(args, entryKey?)` |
| `clutch.trigger(args, key?)` | `clutch.trigger(args, entryKey?)` |
| `clutch.setKey(key)` | `clutch.setEntryKey(entryKey)` |
| `TPackedCommand.key` | `TBoundCommand.entryKey` |
| `useCommand(command, key?)` | `useCommand(command, entryKey?)` |

Опция команды `key` (идентификатор команды, префикс ключей кэша и devtools) и `requestId`
(токен идемпотентности для `queryFn`) **не меняются**. Позиционные параметры сменили имя,
а не позицию.

### pack → bind

Инертный дескриптор «ресурс или команда + args» назван по прецеденту `Function.prototype.bind`:
фиксирует аргументы, вызов потом. Форма дескриптора и поле `kind` не изменились.

| Было | Стало |
|---|---|
| `resource.pack(args)` | `resource.bind(args)` |
| `command.pack(args, key?)` | `command.bind(args, entryKey?)` |
| `TPackedResource`, `TPackedCommand` | `TBoundResource`, `TBoundCommand` |
| `TPacked` | `TBound` |

```typescript
// Было
const packed: TPacked<number, User> = userResource.pack(42);

// Стало
const bound: TBound<number, User> = userResource.bind(42);
```

Подробности — в [API ресурса](../query/api/resource.md#bind).

### set → switch

`set(args, mark?)` стал `switch(args, options?)`: булев второй параметр превратился в поле
объекта опций. Семантика прежняя — `markPending` заставляет ещё не запущенное сцепление отдавать
`pending` вместо `idle`.

```typescript
// Было
clutch.set({ page: 1 });
clutch.set({ page: 1 }, true);
clutch.set(SKIP);

// Стало
clutch.switch({ page: 1 });
clutch.switch({ page: 1 }, { markPending: true });
clutch.switch(SKIP);
```

`switch` — зарезервированное слово, но как имя метода допустимо; деструктуризация метода не
работала и раньше (он опирается на `this`).

### IResourceLiteState → TResourceEntryState

Тип результата `resource.getState(args)`. Префикс `I` на объединении и слово «Lite», не
говорящее, что это, заменены на конвенцию.

| Было | Стало |
|---|---|
| `IResourceLiteState` | `TResourceEntryState` |
| `TResourceLiteIdleState` | `TResourceEntryIdleState` |
| `TResourceLitePendingState` | `TResourceEntryPendingState` (объединение `…PendingNoneState` и `…PendingCurrentState`) |
| `TResourceLiteSuccessState` | `TResourceEntrySuccessState` |
| `TResourceLiteErrorState` | `TResourceEntryErrorState` |

Алиасов нет: вместе с именем изменилась форма, см.
[Состояние записи (getState)](#состояние-записи-getstate). Сам вызов `getState` не изменился.

### Префиксы типов

Конвенция: `T` — типы, `I` — интерфейсы, классы без префикса.

| Было | Стало |
|---|---|
| `Args<TArgs>` | `TArgsOrKeyed<TArgs>` |
| `ArgsOrVoid<TArgs>` | `TArgsOrVoid<TArgs>` |
| `ArgsOrVoidOrSkip<TArgs>` | `TArgsOrVoidOrSkip<TArgs>` |
| `Keyed<T>` | `TKeyed<T>` |
| `PluginHKT` | `IPluginHKT` |
| `ReactHooksPluginHKT` | `IReactHooksPluginHKT` |
| `CombinePluginResourceAugments` | `TCombinePluginResourceAugments` |
| `CombinePluginCommandAugments` | `TCombinePluginCommandAugments` |
| `CombinePluginProjectionResourceAugments` | `TCombinePluginProjectionResourceAugments` |

```typescript
// Было
import type { Args, Keyed, ReactHooksPluginHKT } from '@fozy-labs/rx-toolkit';

// Стало
import type { TArgsOrKeyed, TKeyed, IReactHooksPluginHKT } from '@fozy-labs/rx-toolkit';
```

`TArgs` вместо `Args` невозможен: имя занято generic-параметром по всей библиотеке.

### composeHooks → массив хуков

`onQueryStarted` и `onCacheEntryAdded` у `createApi`, `createResource`, `createCommand` и
`unstable_createProjectionResource` принимают `THook | Array<THook | undefined | false>`.
Falsy-элементы пропускаются, поэтому условный хук пишется на месте.

```typescript
// Было
import { composeHooks } from '@fozy-labs/rx-toolkit';

api.createResource({
    queryFn,
    onQueryStarted: composeHooks(logQueryStarted, isDev ? collectMetrics : undefined),
});

// Стало
api.createResource({
    queryFn,
    onQueryStarted: [logQueryStarted, isDev && collectMetrics],
});
```

Семантика та же: хуки стартуют одновременно, порядок в массиве порядок выполнения не задаёт,
ошибка каждого подавляется независимо. `composeHooks` работает с `@deprecated` до 0.14.0.
Подробности — в [Lifecycle-хуках](../query/usage/lifecycle.md).

### Имя модуля

Модуль называется **Query**; «RxQuery» из документации убран. На импорты и API это не влияет.


## Состояние сцепления ресурса

`TResourceClutchState` перестроен в матрицу. `status` отвечает только на вопрос «идёт ли запрос
и чем кончился прошлый»: `'idle' | 'pending' | 'success' | 'error'`. Что показано на экране,
говорит новое поле `dataSource`: `'none' | 'placeholder' | 'previous' | 'current'`.

Полная таблица из 14 строк и диаграмма переходов — в
[API сцепления ресурса](../query/api/resource-clutch.md#варианты-состояния).

### Флаги: что чем заменить

| Было (0.12.x) | Стало (0.13.0) | Примечание |
|---|---|---|
| `isLoading` | `isPending` | точный эквивалент |
| `isInitialLoading` | `isInitialLoading` | формула шире: загрузка под плейсхолдером тоже считается |
| `isSwitching` | `isSwitching` | без изменений |
| `isRefreshing` | `isInvalidating \|\| isSwitching` | старый флаг покрывал и смену args; только фоновое обновление текущих args — это `isInvalidating` |
| `isRefreshError` | `status === 'error' && dataSource === 'current'` | практически — `status === 'error' && hasData` |
| `isRetrying` | `isPending && hasError` | отдельного флага нет: повтор в полёте ⇔ ошибка ещё в `error` |
| `isSuccess` | `status === 'success'` | для рендера данных нужен `hasData`, а не этот флаг |
| `isError` | `status === 'error'` | `hasError` **шире**: он переживает повтор |
| `status === 'refreshing'` | `isPending && hasData` | точно для текущих args — `isInvalidating` |
| `status === 'refresh-error'` | `status === 'error' && hasData` | точно — `dataSource === 'current'` |
| `data !== null` | `hasData` | см. [ниже](#hasdata-вместо-проверки-data) |

Добавлены `dataSource`, `hasData`, `hasError`, `isPending`, `isInvalidating`.
`isInitialLoading + isSwitching + isInvalidating = isPending`: при запросе в полёте истинен
ровно один из трёх.

### Статус error стал шире

В 0.12.x `status: 'error'` означал «упало, показать нечего» (и SWR-остаток при смене args), а
провал фонового обновления был отдельным статусом `'refresh-error'`. Теперь `status: 'error'`
покрывает все четыре ошибочные строки матрицы — 7, 8, 9 и 13, — а различает их `dataSource`.

```tsx
// Было
if (state.status === 'refresh-error') {
    return <StaleBanner data={state.data} error={state.error} />;
}
if (state.status === 'error') {
    return <ErrorPanel error={state.error} />;
}

// Стало
if (state.status === 'error' && state.hasData) {
    return <StaleBanner data={state.data} error={state.error} />;
}
if (state.status === 'error') {
    return <ErrorPanel error={state.error} />;
}
```

Код, который раньше ловил `status === 'error'` как «нечего показывать», после обновления начнёт
срабатывать и на упавшей инвалидации: экран с готовыми данными сменится панелью ошибки.
Гейт — `hasData`.

### switch (status) больше не разбиение

Статусов стало четыре, но они больше не описывают экран в одиночку: строка 6 (инвалидация
текущих args) — это `status: 'pending'` при свежих данных на экране. `switch (status)` без
проверки `hasData` покажет спиннер на каждой инвалидации — в 0.12.x у неё был свой статус
`'refreshing'`, и такой `switch` работал.

```tsx
// Было
switch (state.status) {
    case 'pending': return <Spinner />;
    case 'refreshing': return <List items={state.data} stale />;
    case 'success': return <List items={state.data} />;
    case 'refresh-error':
    case 'error': return <ErrorPanel error={state.error} />;
    case 'idle': return null;
}

// Стало — сначала «есть что показать», потом ошибка, потом загрузка
if (state.hasData) {
    return <List items={state.data} stale={state.isPending} error={state.error} />;
}
if (state.hasError) {
    return <ErrorPanel error={state.error} retrying={state.isPending} onRetry={state.retry} />;
}
if (state.isPending) {
    return <Spinner />;
}
return null; // idle
```

Сужение при этом не потерялось: каждый вариант несёт литеральные `status`, `dataSource` и
`hasData` / `hasError`, поэтому `state.hasData` даёт `data: TData` без `| null`, а
`state.hasError` — `error: TError`.

### hasData вместо проверки data

`TData` может сам быть `null` (например, `queryFn`, отдающий «ничего не найдено» как `null`).
Поэтому `data !== null` и `data &&` — не замена `hasData`: строка со свежими данными `null`
даёт `hasData: true` при `data === null`, и проверка по значению отправит такой экран
в загрузку или в ошибку.

```tsx
// Было
if (query.data) { /* … */ }

// Стало
if (query.hasData) { /* … */ }
```

Ровно по этой причине `dataSource` — единственный источник истины о наличии данных, а
`hasData` — его сокращение (`dataSource !== 'none'`).

### placeholderData

Новая опция ресурса: пока для этих args ничего не закэшировано, сцепление показывает
синтезированные данные как `dataSource: 'placeholder'`.

```typescript
const userResource = api.createResource({
    queryFn: (id: number) => fetchUser(id),
    placeholderData: (id) => {
        const item = usersListResource.getState().data?.find((u) => u.id === id);
        return item ? { data: item } : null;
    },
});
```

Опция аддитивна: без неё поведение прежнее (`previous` → `none`). Правила вызова и сброса
memo — в [API ресурса](../query/api/resource.md#placeholderdata). Проекционные ресурсы
(и, как следствие, страницы `useInfiniteResource`) опцию не поддерживают.


## Состояние записи (getState)

`resource.getState(args)` возвращает тот же тип, что и сцепление, с `dataSource`, суженным до
`'none' | 'current'`: у записи нет ни previous, ни плейсхолдера. Методов (`retry` / `invalidate`)
в нём нет — они есть у [записи кэша](../query/concepts/cache.md). Матрица записи — строки
1, 2, 5, 6, 7, 9, 10, 12; `isSwitching` там всегда `false`.

Таблица замен та же, что [у сцепления](#флаги-что-чем-заменить).

```typescript
// Было
if (usersResource.getState({ page: 1 }).isError) { /* … */ }

// Стало
if (usersResource.getState({ page: 1 }).status === 'error') { /* … */ }
```


## useSuspenseResource

Порядок решения стал явным: `hasData` → вернуть состояние; `status === 'error'` → бросить
ошибку в Error Boundary; иначе приостановить рендер.

| Ситуация | 0.12.x | 0.13.0 |
|---|---|---|
| Ошибка, показать нечего (строка 7) | бросается | бросается |
| Ошибка поверх данных предыдущих args (строка 8) | возвращалась только при `data != null` | возвращается всегда |
| Ошибка поверх плейсхолдера (строка 13) | плейсхолдеров не было | возвращается |
| Инвалидация и её провал | не приостанавливает | не приостанавливает |

Практическое следствие: с `TData`, допускающим `null`, ошибка поверх данных предыдущих args
раньше долетала до Error Boundary, а теперь приходит в состоянии — читайте `hasError`.

Возвращаемый тип — `TResourceClutchState`, суженный по
`dataSource: 'placeholder' | 'previous' | 'current'`; тип `TSuspenseResourceErrorState` удалён.

```tsx
// Было
const { data, isRefreshing, isRefreshError } = userResource.useSuspenseResource({ id });

// Стало
const { data, isInvalidating, hasError } = userResource.useSuspenseResource({ id });
```

Подробности — в [React-хуках](../usage/react/README.md#usesuspenseresource).


## useInfiniteResource

| Было | Стало |
|---|---|
| `isIdle` | `isIdle` |
| `isInitialLoading` | `isInitialLoading` |
| `isLoading` | `isPending` |
| `isFetchingNext` | `isLoadingNext` |
| `isError` | `hasError` |
| `error` | `error` |
| — | `isInvalidating` (страница перезапрашивается поверх своих данных) |
| — | `hasData` |
| `refresh()` | `invalidate()` (алиас `refresh` до 0.14.0) |

```tsx
const feed = postsProjection.useInfiniteResource(firstPageIds);

// Было
feed.isLoading; feed.isFetchingNext; feed.isError; feed.refresh();

// Стало
feed.isPending; feed.isLoadingNext; feed.hasError; feed.invalidate();
```

Изменилось и содержимое `data`: в него попадают элементы только тех страниц, у которых есть
данные **своих** args (`dataSource: 'current'`), — раньше все страницы с `data !== null`.
Три флага загрузки — не разбиение `isPending`, а «есть хоть одна такая страница»: после
`invalidate()` ленты с упавшей последней страницей `isInvalidating` и `isLoadingNext` истинны
одновременно. Таблица формул — в
[Проекционном ресурсе](../query/usage/projection-resource.md).


## Состояние сцепления команды

У команды нет ни previous, ни смены args, ни плейсхолдера, поэтому набор полей короче:
`status`, `data`, `error`, `args`, `isPending`, `hasData`, `hasError`, метод `retry()`.

| Было | Стало |
|---|---|
| `isLoading` | `isPending` |
| `isSuccess` | `hasData` (⇔ `status === 'success'`) |
| `isError` | `status === 'error'`; `hasError` **шире** — переживает повтор |

```tsx
// Было
const [trigger, { isLoading, isSuccess, isError, error }] = addTodoCommand.useCommand();

// Стало
const [trigger, { isPending, hasData, hasError, error }] = addTodoCommand.useCommand();
```

В `pending` данных больше нет вообще: `data` типизирован строго `null`. Раньше туда могли
просочиться значения прошлого запуска через защитный remap статусов `refreshing` /
`refresh-error`; теперь эти статусы для команды недостижимы — `invalidate()` на записи команды
выводит `console.warn` и ничего не делает. Строки состояния (К1–К5) — в
[API сцепления команды](../query/api/command-clutch.md#варианты-состояния).


## invalidate() на упавшей записи

В машине появился переход `error → pending` с обнулением ошибки, и `invalidate()` его разрешает.
Публичное следствие: **`resource.invalidate(args)` и `entry.invalidate()` на записи в статусе
`error` теперь перезапускают запрос и снимают ошибку**, а в 0.12.3 `refresh()` писал
предупреждение в консоль и ничего не делал.

```typescript
// 0.12.x: no-op + console.warn на упавшей записи
usersResource.refresh({ page: 1 });

// 0.13.0: перезапускает запрос и снимает ошибку
usersResource.invalidate({ page: 1 });

// Нужно сохранить ошибку на экране — это retry, а не инвалидация
usersResource.getEntry({ page: 1 })?.retry();
```

Код, который вызывал `refresh()` вслепую (например, по фокусу окна или по таймеру) и полагался
на то, что упавшая запись останется упавшей, после обновления начнёт её перезапрашивать.

Сцепление при этом продолжает отклонять `invalidate()` там, где показывать нечего (строка 7
матрицы): `console.warn` и no-op. Переход нужен рёбрам «ошибка поверх previous или плейсхолдера
→ перезапрос», которые машине не видны. Диаграмма — в
[Машине состояний](../query/concepts/machine.md).


## Снимки: версия 2

`CURRENT_SNAPSHOT_VERSION` поднят до `2`: в снимке статус машины хранится строкой, а строки
переименованы.

| Направление | Поведение |
|---|---|
| 0.13.0 читает снимок версии 1 | `refreshing` / `refresh-error` трактуются как `invalidating` / `invalidate-error` |
| 0.12.x читает снимок версии 2 | записи с `invalidate-error` не гидрируются — такой статус ей незнаком |

Для SSR это значит: клиент и сервер обновляются вместе. Смешанный деплой, где старый клиент
читает снимок нового сервера, теряет часть записей (они просто загрузятся заново).
См. [Снимки](../query/usage/snapshot.md).

## Что не изменилось

- `Resource`, `Command`, `queryFn`, `links`, `SKIP`, `retentionTime`, `mapError`.
- `ensure` / `fetch` / `prefetch`, `command.execute`, `command.trigger`,
  `unstable_createProjectionResource`.
- `clutch.start()`, `clutch.adoptPrevious()`, `clutch.retry()`, `clutch.whenSettled()`,
  `clutch.trigger()` — имена и контракты прежние. Условие резолва `whenSettled` то же самое:
  есть что отрисовать либо запрос упал, не оставив ничего на экране.
- Конверт результата `trigger` (`TTriggerResult` / `TTriggerPromise`, `unwrap()`), `wrapTrigger`.
- Опция команды `key` и `requestId`.
- Вызов `resource.getState(args)` — изменился только тип результата.
- `isSwitching` — имя и формула. `isInitialLoading` сохранил имя; формула учла плейсхолдер.

## Удалено без алиасов

Алиас на изменившуюся форму был бы ложью, поэтому его нет.

- Флаги состояния сцепления ресурса и записи: `isLoading`, `isRefreshing`, `isRefreshError`,
  `isRetrying`, `isSuccess`, `isError`.
- Флаги `useInfiniteResource`: `isLoading`, `isFetchingNext`, `isError`.
- Флаги состояния команды: `isLoading`, `isSuccess`, `isError`.
- Статусы `'refreshing'` / `'refresh-error'` — переименованы в машине и полностью убраны из
  состояния сцепления и записи.
- Поле `isRetrying` в состояниях машины `TPendingState` / `TInvalidatingState`: повтор в полёте
  определяется по `error !== null`.
- Типы `TRetrying`, `TSuspenseResourceErrorState`, а также варианты состояния, описывавшие
  статусы `refreshing` / `refresh-error`: `TResourceAgentRefreshingState`,
  `TResourceAgentRefreshErrorState`, `TResourceLiteRefreshingState`,
  `TResourceLiteRefreshErrorState` — вместе с формами, которые они описывали. Их строки
  матрицы теперь покрывают `TResourceClutchPendingCurrentState` и `TResourceClutchErrorState`.
- Классы и типы машины `MachineRefreshing` / `MachineRefreshError` / `TRefreshingState` /
  `TRefreshErrorState` — переименованы, см. [refresh → invalidate](#refresh--invalidate).
