# Миграция с версии 0.12.x на 0.13.0

Релиз меняет в модуле Query три вещи сразу.

- **Словарь.** «Агент» стал «сцеплением» (`Clutch`), `refresh` — `invalidate`, `pack` — `bind`,
  ключ записи у команды — `entryKey`. Чистые переименования прикрыты `@deprecated`-алиасами:
  код компилируется как есть и работает один релиз, [до 0.14.0](#deprecated-удаляется-в-0140).
- **Форма реактивного состояния.** Состояние сцепления ресурса стало матрицей
  `status` × `dataSource`, у команды и у бесконечной ленты поменялся набор флагов.
  Здесь алиасов нет: удалённые поля компилятор покажет поимённо.
- **Состояние записи кэша стало плоским.** `entry.state$()` отдаёт запись без обёртки `.state`,
  `entry.machine$` удалён, классы `Machine*` ушли из публичного API. Имена типов состояния
  прикрыты алиасами, форма доступа — нет.

Опасны не они, а места, где код продолжает компилироваться, а ведёт себя иначе. Их восемь,
все разобраны ниже: [`status === 'error'` стал шире](#статус-error-стал-шире),
[`switch (status)` перестал быть разбиением](#switch-status-больше-не-разбиение),
[`entryKey` в дескрипторе команды](#key--entrykey),
[`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи),
[инвалидация ленивая](#инвалидация-ленивая),
[`invalidate()` при запросе в полёте](#invalidate-при-запросе-в-полёте),
[`fetch()` при запросе в полёте](#fetch-при-запросе-в-полёте) и
[чтение `.state` у записи за нетипизированной границей](#state-отдаёт-плоскую-запись).

Вне Query — одна правка: [`LocalSignal` принимает `schema` вместо `zodSchema`](#localsignal-zodschema--schema).

Заодно удалены API, объявленные deprecated ещё в 0.11.1: `resource.trigger()`, `command.trigger()`
и `signalize`, см. [Удалены deprecated из 0.11.1](#удалены-deprecated-из-0111).

## Порядок миграции

1. Обновиться и собрать проект. Всё, что компилятор покажет сразу, — это форма состояния,
   плоский `entry.state$()`, пропавшие из публичного API классы `Machine*`,
   [изменённые интерфейсы и типы опций](#интерфейсы-и-типы-опций) и
   [удалённые deprecated из 0.11.1](#удалены-deprecated-из-0111); алиасы остальное скрывают.
2. Пройти [таблицу флагов](#флаги-что-чем-заменить) и заменить чтения состояния.
3. Перечитать восемь мест, на которые компилятор не укажет (или укажет не везде):
   [`status === 'error'`](#статус-error-стал-шире),
   [`switch (status)`](#switch-status-больше-не-разбиение),
   [`entryKey` в дескрипторе](#key--entrykey),
   [`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи),
   [инвалидация ленивая](#инвалидация-ленивая),
   [`invalidate()` при запросе в полёте](#invalidate-при-запросе-в-полёте),
   [`fetch()` при запросе в полёте](#fetch-при-запросе-в-полёте),
   [`.state` у записи кэша](#state-отдаёт-плоскую-запись).
4. Переименовать словарь по [таблицам](#словарь) — алиасы дают на это время до 0.14.0,
   но чем раньше, тем меньше смешанной терминологии в коде.


## Словарь

### Agent → Clutch

Термин `Agent` обещал автономию, которой у объекта нет, и конфликтовал с ИИ-агентами.
Сцепление (clutch) соединяет потребителя с записью кэша и переключает записи, не останавливая
ресурс, — [метафора разобрана в концепции](../query/concepts/clutch.md).

| Было (0.12.x) | Стало (0.13.0) |
|---|---|
| `ResourceAgent`, `CommandAgent` | `ResourceClutch`, `CommandClutch` |
| `IResourceAgent`, `ICommandAgent` | `IResourceClutch`, `ICommandClutch` |
| `TResourceAgentState` + варианты | `TResourceClutchState` + варианты |
| `TCommandAgentState` + варианты | `TCommandClutchState` + варианты |
| `TAgentStatus` | `TClutchStatus` |
| `resource.createAgent()` | `resource.createClutch()` |
| `command.createAgent(key?)` | `command.createClutch(entryKey?)` |

```typescript
// Было
const agent = usersResource.createAgent();

// Стало
const clutch = usersResource.createClutch();
```

`TAgentStatus` остаётся алиасом, но **набор значений сузился**: было
`'idle' | 'pending' | 'success' | 'error' | 'refreshing' | 'refresh-error'`, стало четыре
значения `TClutchStatus`. Код, перечисляющий статусы вручную, алиас не спасёт — см.
[Статус error стал шире](#статус-error-стал-шире).

### refresh → invalidate

Один корень на «пометить устаревшим и перезапросить в фоне» на всех уровнях.

| Уровень | Было | Стало |
|---|---|---|
| `Resource` | `refresh(args)` | `invalidate(args)` |
| Запись кэша | `entry.refresh()` | `entry.invalidate()` |
| Сцепление ресурса | `clutch.refresh()` | `clutch.invalidate()` |
| Состояние сцепления | `state.refresh()` | `state.invalidate()` |
| `useInfiniteResource` | `feed.refresh()` | `feed.invalidate()` |

```typescript
// Было
usersResource.refresh({ page: 1 });

// Стало
usersResource.invalidate({ page: 1 });
```

Семантика вызова не изменилась ни на одном уровне, кроме трёх случаев —
[`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи),
[записи без подписчиков](#инвалидация-ленивая) и
[записи с запросом в полёте](#invalidate-при-запросе-в-полёте).

**Статусы записи кэша.** То, что хранит сама запись, тоже переименовано:

| Было | Стало |
|---|---|
| статусы `'refreshing'`, `'refresh-error'` | `'invalidating'`, `'invalidate-error'` |
| типы `TRefreshingState`, `TRefreshErrorState` | `TQueryEntryInvalidatingState`, `TQueryEntryInvalidateErrorState` |
| классы `MachineRefreshing`, `MachineRefreshError` | не экспортируются, см. [Состояние записи кэша](#состояние-записи-кэша) |
| `entry.refresh()` | `entry.invalidate()` |

```typescript
// Было
if (entry.machine$().status === 'refresh-error') { /* … */ }

// Стало
if (entry.state$().status === 'invalidate-error') { /* … */ }
```

Обращение к состоянию записи изменилось целиком — см.
[Состояние записи кэша](#состояние-записи-кэша).

Из `TQueryEntryPendingState` и `TQueryEntryInvalidatingState` убрано поле `isRetrying`: повтор
в полёте — это `error !== null`. Статусы `invalidating` / `invalidate-error` **у записи кэша**
остались; из состояния сцепления и `getState()` они ушли, см.
[матрицу](../query/api/resource-clutch.md#варианты-состояния).

### key → entryKey

Начните с этого пункта: **дескриптор команды — единственное переименование, от которого алиас
не защищает.** У `TBoundCommand` поле `key` стало `entryKey`, а `@deprecated`-алиас
`TPackedCommand` указывает на новый тип и старое поле не сохраняет.

```typescript
// Было
const { key } = addTodoCommand.pack({ text: 'Задача' }, 'my-key');

// Стало
const { entryKey } = addTodoCommand.bind({ text: 'Задача' }, 'my-key');
```

В типизированном коде компилятор укажет на деструктуризацию (`Property 'key' does not exist`).
Но там, где дескриптор проходит через нетипизированную границу — JS, `any`, собственный реестр
или транспорт, — чтение `.key` молча даёт `undefined`, и команда запускается со сгенерированным
ключом вместо общего. Найдите чтения поля грепом.

У команды под словом `key` жили две разные вещи. Переименовывается только ключ записи кэша:

| Было | Стало |
|---|---|
| `command.execute(args, key?)` | `command.execute(args, entryKey?)` |
| `command.createAgent(key?)` | `command.createClutch(entryKey?)` |
| `command.pack(args, key?)` | `command.bind(args, entryKey?)` |
| `clutch.trigger(args, key?)` | `clutch.trigger(args, entryKey?)` |
| `clutch.setKey(key)` | `clutch.setEntryKey(entryKey)` |
| `TPackedCommand.key` | `TBoundCommand.entryKey` |
| `useCommand(command, key?)` | `useCommand(command, entryKey?)` |

Опция команды `key` (идентификатор команды, префикс ключей кэша и devtools) и `requestId`
(токен идемпотентности для `queryFn`) **не меняются**. Позиционные параметры сменили имя,
а не позицию.

### pack → bind

Инертный дескриптор «ресурс или команда + args» назван по прецеденту `Function.prototype.bind`:
фиксирует аргументы, вызов потом. Форма дескриптора и поле `kind` не изменились.

| Было | Стало |
|---|---|
| `resource.pack(args)` | `resource.bind(args)` |
| `command.pack(args, key?)` | `command.bind(args, entryKey?)` |
| `TPackedResource`, `TPackedCommand` | `TBoundResource`, `TBoundCommand` |
| `TPacked` | `TBound` |

```typescript
// Было
const packed: TPacked<number, User> = userResource.pack(42);

// Стало
const bound: TBound<number, User> = userResource.bind(42);
```

Подробности — в [API ресурса](../query/api/resource.md#bind).

### set → switch

`set(args, mark?)` стал `switch(args, options?)`: булев второй параметр превратился в поле
объекта опций. Семантика прежняя — `markPending` заставляет ещё не запущенное сцепление отдавать
`pending` вместо `idle`.

```typescript
// Было
clutch.set({ page: 1 });
clutch.set({ page: 1 }, true);
clutch.set(SKIP);

// Стало
clutch.switch({ page: 1 });
clutch.switch({ page: 1 }, { markPending: true });
clutch.switch(SKIP);
```

`switch` — зарезервированное слово, но как имя метода допустимо; деструктуризация метода не
работала и раньше (он опирается на `this`).

### IResourceLiteState → TResourceEntryState

Тип результата `resource.getState(args)`. Префикс `I` на объединении и слово «Lite», не
говорящее, что это, заменены на конвенцию.

| Было | Стало |
|---|---|
| `IResourceLiteState` | `TResourceEntryState` |
| `TResourceLiteIdleState` | `TResourceEntryIdleState` |
| `TResourceLitePendingState` | `TResourceEntryPendingState` (объединение `…PendingNoneState` и `…PendingCurrentState`) |
| `TResourceLiteSuccessState` | `TResourceEntrySuccessState` |
| `TResourceLiteErrorState` | `TResourceEntryErrorState` |

Алиасов нет: вместе с именем изменилась форма, см.
[Состояние записи (getState)](#состояние-записи-getstate). Сам вызов `getState` не изменился.

### Префиксы типов

Конвенция: `T` — типы, `I` — интерфейсы, классы без префикса.

| Было | Стало |
|---|---|
| `Args<TArgs>` | `TArgsOrKeyed<TArgs>` |
| `ArgsOrVoid<TArgs>` | `TArgsOrVoid<TArgs>` |
| `ArgsOrVoidOrSkip<TArgs>` | `TArgsOrVoidOrSkip<TArgs>` |
| `Keyed<T>` | `TKeyed<T>` |
| `PluginHKT` | `IPluginHKT` |
| `ReactHooksPluginHKT` | `IReactHooksPluginHKT` |
| `CombinePluginResourceAugments` | `TCombinePluginResourceAugments` |
| `CombinePluginCommandAugments` | `TCombinePluginCommandAugments` |
| `CombinePluginProjectionResourceAugments` | `TCombinePluginProjectionResourceAugments` |

```typescript
// Было
import type { Args, Keyed, ReactHooksPluginHKT } from '@fozy-labs/rx-toolkit';

// Стало
import type { TArgsOrKeyed, TKeyed, IReactHooksPluginHKT } from '@fozy-labs/rx-toolkit';
```

`TArgs` вместо `Args` невозможен: имя занято generic-параметром по всей библиотеке.

### composeHooks → массив хуков

`onQueryStarted` и `onCacheEntryAdded` у `createApi`, `createResource`, `createCommand` и
`unstable_createProjectionResource` принимают `THook | Array<THook | undefined | false>`.
Falsy-элементы пропускаются, поэтому условный хук пишется на месте.

```typescript
// Было
import { composeHooks } from '@fozy-labs/rx-toolkit';

api.createResource({
    queryFn,
    onQueryStarted: composeHooks(logQueryStarted, isDev ? collectMetrics : undefined),
});

// Стало
api.createResource({
    queryFn,
    onQueryStarted: [logQueryStarted, isDev && collectMetrics],
});
```

Семантика та же: хуки стартуют одновременно, порядок в массиве порядок выполнения не задаёт,
ошибка каждого подавляется независимо. `composeHooks` работает с `@deprecated` до 0.14.0.
Подробности — в [Lifecycle-хуках](../query/usage/lifecycle.md).

### Имя модуля

Модуль называется **Query**; «RxQuery» из документации убран. На импорты и API это не влияет.


## Состояние сцепления ресурса

`TResourceClutchState` перестроен в матрицу. `status` отвечает только на вопрос «идёт ли запрос
и чем кончился прошлый»: `'idle' | 'pending' | 'success' | 'error'`. Что показано на экране,
говорит новое поле `dataSource`: `'none' | 'placeholder' | 'previous' | 'current'`.

Полная таблица из 14 строк и диаграмма переходов — в
[API сцепления ресурса](../query/api/resource-clutch.md#варианты-состояния).

### Флаги: что чем заменить

| Было (0.12.x) | Стало (0.13.0) | Примечание |
|---|---|---|
| `isLoading` | `isPending` | точный эквивалент |
| `isInitialLoading` | `isInitialLoading` | формула шире: загрузка под плейсхолдером тоже считается |
| `isSwitching` | `isSwitching` | без изменений |
| `isRefreshing` | `isInvalidating \|\| isSwitching` | старый флаг покрывал и смену args; только фоновое обновление текущих args — это `isInvalidating` |
| `isRefreshError` | `status === 'error' && dataSource === 'current'` | практически — `status === 'error' && hasData` |
| `isRetrying` | `isPending && hasError` | отдельного флага нет: повтор в полёте ⇔ ошибка ещё в `error` |
| `isSuccess` | `status === 'success'` | для рендера данных нужен `hasData`, а не этот флаг |
| `isError` | `status === 'error'` | `hasError` **шире**: он переживает повтор |
| `status === 'refreshing'` | `isPending && hasData` | точно для текущих args — `isInvalidating` |
| `status === 'refresh-error'` | `status === 'error' && hasData` | точно — `dataSource === 'current'` |
| `data !== null` | `hasData` | см. [ниже](#hasdata-вместо-проверки-data) |

Добавлены `dataSource`, `hasData`, `hasError`, `isPending`, `isInvalidating`.
`isInitialLoading + isSwitching + isInvalidating = isPending`: при запросе в полёте истинен
ровно один из трёх.

### Статус error стал шире

В 0.12.x `status: 'error'` означал «упало, показать нечего» (и SWR-остаток при смене args), а
провал фонового обновления был отдельным статусом `'refresh-error'`. Теперь `status: 'error'`
покрывает все четыре ошибочные строки матрицы — 7, 8, 9 и 13, — а различает их `dataSource`.

```tsx
// Было
if (state.status === 'refresh-error') {
    return <StaleBanner data={state.data} error={state.error} />;
}
if (state.status === 'error') {
    return <ErrorPanel error={state.error} />;
}

// Стало
if (state.status === 'error' && state.hasData) {
    return <StaleBanner data={state.data} error={state.error} />;
}
if (state.status === 'error') {
    return <ErrorPanel error={state.error} />;
}
```

Код, который раньше ловил `status === 'error'` как «нечего показывать», после обновления начнёт
срабатывать и на упавшей инвалидации: экран с готовыми данными сменится панелью ошибки.
Гейт — `hasData`.

### switch (status) больше не разбиение

Статусов стало четыре, но они больше не описывают экран в одиночку: строка 6 (инвалидация
текущих args) — это `status: 'pending'` при свежих данных на экране. `switch (status)` без
проверки `hasData` покажет спиннер на каждой инвалидации — в 0.12.x у неё был свой статус
`'refreshing'`, и такой `switch` работал.

```tsx
// Было
switch (state.status) {
    case 'pending': return <Spinner />;
    case 'refreshing': return <List items={state.data} stale />;
    case 'success': return <List items={state.data} />;
    case 'refresh-error':
    case 'error': return <ErrorPanel error={state.error} />;
    case 'idle': return null;
}

// Стало — сначала «есть что показать», потом ошибка, потом загрузка
if (state.hasData) {
    return <List items={state.data} stale={state.isPending} error={state.error} />;
}
if (state.hasError) {
    return <ErrorPanel error={state.error} retrying={state.isPending} onRetry={state.retry} />;
}
if (state.isPending) {
    return <Spinner />;
}
return null; // idle
```

Сужение при этом не потерялось: каждый вариант несёт литеральные `status`, `dataSource` и
`hasData` / `hasError`, поэтому `state.hasData` даёт `data: TData` без `| null`, а
`state.hasError` — `error: TError`.

### hasData вместо проверки data

`TData` может сам быть `null` (например, `queryFn`, отдающий «ничего не найдено» как `null`).
Поэтому `data !== null` и `data &&` — не замена `hasData`: строка со свежими данными `null`
даёт `hasData: true` при `data === null`, и проверка по значению отправит такой экран
в загрузку или в ошибку.

```tsx
// Было
if (query.data) { /* … */ }

// Стало
if (query.hasData) { /* … */ }
```

Ровно по этой причине `dataSource` — единственный источник истины о наличии данных, а
`hasData` — его сокращение (`dataSource !== 'none'`).

### placeholderData

Новая опция ресурса: пока для этих args ничего не закэшировано, сцепление показывает
синтезированные данные как `dataSource: 'placeholder'`.

```typescript
const userResource = api.createResource({
    queryFn: (id: number) => fetchUser(id),
    placeholderData: (id) => {
        const item = usersListResource.getState().data?.find((u) => u.id === id);
        return item ? { data: item } : null;
    },
});
```

Опция аддитивна: без неё поведение прежнее (`previous` → `none`). Правила вызова и сброса
memo — в [API ресурса](../query/api/resource.md#placeholderdata). Проекционные ресурсы
(и, как следствие, страницы `useInfiniteResource`) опцию не поддерживают.


## Состояние записи (getState)

`resource.getState(args)` возвращает тот же тип, что и сцепление, с `dataSource`, суженным до
`'none' | 'current'`: у записи нет ни previous, ни плейсхолдера. Методов (`retry` / `invalidate`)
в нём нет — они есть у [записи кэша](../query/concepts/cache.md). Матрица записи — строки
1, 2, 5, 6, 7, 9, 10, 12; `isSwitching` там всегда `false`.

Таблица замен та же, что [у сцепления](#флаги-что-чем-заменить).

```typescript
// Было
if (usersResource.getState({ page: 1 }).isError) { /* … */ }

// Стало
if (usersResource.getState({ page: 1 }).status === 'error') { /* … */ }
```


## Состояние записи кэша

Не путать с предыдущим разделом: там — производное состояние, которое ресурс отдаёт наружу
(`TResourceEntryState`, с `dataSource` и флагами). Здесь — **сырая запись, которую хранит сама
кэш-запись** (`TQueryEntryState`): пять статусов, `data`, `error`, `updatedAt`, `patchState`.
Концепция целиком — в [Состоянии записи запроса](../query/concepts/query-entry-state.md).

До 0.13.0 эта запись была завёрнута в публичный класс `Machine`. Теперь класс — деталь
реализации ядра, а наружу идёт плоская запись.

### state$ отдаёт плоскую запись

Обёртки `.state` больше нет — у `entry.state$()`, `entry.peek()` и `entry.set()` один и тот же
плоский тип `TQueryEntryState<TArgs, TData>`.

```typescript
// Было
const status = entry.state$().state.status;
const data = entry.peek().state.data;

// Стало
const status = entry.state$().status;
const data = entry.peek().data;
```

Компилятор укажет на каждое обращение к `.state` (`Property 'state' does not exist`). Опасно
одно место: чтение состояния за нетипизированной границей (JS, `any`, собственный логгер,
сериализация записи) — там `.state` молча даст `undefined`. Найдите `.state$().state`
и `.peek().state` грепом.

### entry.machine$ удалён

Отдельного сигнала с экземпляром машины больше нет: состояние записи публикует `state$` — той же плоской записью.

```typescript
// Было
entry.machine$().status;
entry.machine$().data;

// Стало
entry.state$().status;
entry.state$().data;
```

### Классы Machine* не экспортируются

`Machine`, `MachineBase`, `MachineWithData`, `MachinePending`, `MachineSuccess`, `MachineError`,
`MachineInvalidating`, `MachineInvalidateError` убраны из публичного API **без алиасов**: импорт
перестанет резолвиться. Слово `Machine` целиком отошло модулю
[Statechart](../statechart/README.md).

```typescript
// Было
import { MachineSuccess } from '@fozy-labs/rx-toolkit';

function isFresh(entry: IQueryCacheEntry<number, User>) {
    return entry.machine$() instanceof MachineSuccess;
}

// Стало — проверка по статусу плоской записи
function isFresh(entry: IQueryCacheEntry<number, User>) {
    return entry.state$().status === 'success';
}
```

Код, который вызывал переходы напрямую (`machine.success(data)`, `machine.fail(error)`,
`machine.rebase(data)`, `machine.next(data)`), опирался на внутренности. Публичные входы —
`entry.invalidate()`, `entry.retry()` и `entry.createPatch()`; остальные переходы запись делает
сама, завершая запрос.

### initialMachine → initialState

Опция `initialState` в `IQueryCacheEntryOptions` принимает плоскую запись; всё остальное
`QueryCacheEntry` делает сама.

```typescript
// Было — состояние собиралось статическим конструктором машины
initialMachine: Machine.fromSnapshot({ args, data, updatedAt }),

// Стало — плоская запись
initialState: { status: 'success', args, data, error: null, updatedAt, patchState: null },
```

Переданное состояние подавляет автоматический первый запуск. Устаревший снимок — не статус
`invalidating`, а опция `isInvalidated: true` при `success`: запись рождается помеченной и
перезапрашивается при первом удержании, см. [Инвалидация ленивая](#инвалидация-ленивая).

### beforeDevtoolsPush получает плоскую запись

Опция записи кэша типизирована через `TQueryEntryState<TArgs, TData>`. Практическое следствие:
в Redux DevTools теперь уходит плоская запись, а не сериализованный экземпляр `Machine` с полем
`state` внутри. Записанные сессии и обработчики, лазившие в `state.*`, надо поправить.

```typescript
// Было — в хук приходил экземпляр Machine, состояние лежало в machine.state
beforeDevtoolsPush: (machine, push) => {
    console.log(machine.state.status);
    push(machine);
},

// Стало — приходит плоская запись TQueryEntryState
beforeDevtoolsPush: (state, push) => {
    console.log(state.status);
    push(state);
},
```

### Переименование типов состояния записи

Переименование чистое — форму эти типы сохраняют, поэтому `@deprecated`-алиасы живут
[до 0.14.0](#deprecated-удаляется-в-0140). Поле `isRetrying` из `pending` / `invalidating` убрано
отдельным изменением, см. [refresh → invalidate](#refresh--invalidate).

| Было | Стало |
|---|---|
| `TMachineState` | `TQueryEntryState` |
| `TMachineStatus` | `TQueryEntryStatus` |
| `TPendingState` | `TQueryEntryPendingState` |
| `TSuccessState` | `TQueryEntrySuccessState` |
| `TErrorState` | `TQueryEntryErrorState` |
| `TInvalidatingState` | `TQueryEntryInvalidatingState` |
| `TInvalidateErrorState` | `TQueryEntryInvalidateErrorState` |

Имя выбрано по владельцу записи (`QueryCacheEntry`), чтобы не путать её с производным
`TResourceEntryState` из [`resource.getState(args)`](#состояние-записи-getstate): первое — то, что
запись хранит, второе — то, что ресурс показывает наружу. Производные типы
(`TResourceEntryState`, `TResourceClutchState`, `TCommandClutchState`) к этому переименованию
отношения не имеют.


## useSuspenseResource

Порядок решения стал явным: `hasData` → вернуть состояние; `status === 'error'` → бросить
ошибку в Error Boundary; иначе приостановить рендер.

| Ситуация | 0.12.x | 0.13.0 |
|---|---|---|
| Ошибка, показать нечего (строка 7) | бросается | бросается |
| Ошибка поверх данных предыдущих args (строка 8) | возвращалась только при `data != null` | возвращается всегда |
| Ошибка поверх плейсхолдера (строка 13) | плейсхолдеров не было | возвращается |
| Инвалидация и её провал | не приостанавливает | не приостанавливает |

Практическое следствие: с `TData`, допускающим `null`, ошибка поверх данных предыдущих args
раньше долетала до Error Boundary, а теперь приходит в состоянии — читайте `hasError`.

Возвращаемый тип — `TResourceClutchState`, суженный по
`dataSource: 'placeholder' | 'previous' | 'current'`; тип `TSuspenseResourceErrorState` удалён.

```tsx
// Было
const { data, isRefreshing, isRefreshError } = userResource.useSuspenseResource({ id });

// Стало
const { data, isInvalidating, hasError } = userResource.useSuspenseResource({ id });
```

Подробности — в [React-хуках](../usage/react/README.md#usesuspenseresource).


## useInfiniteResource

| Было | Стало |
|---|---|
| `isIdle` | `isIdle` |
| `isInitialLoading` | `isInitialLoading` |
| `isLoading` | `isPending` |
| `isFetchingNext` | `isLoadingNext` |
| `isError` | `hasError` |
| `error` | `error` |
| — | `isInvalidating` (страница перезапрашивается поверх своих данных) |
| — | `hasData` |
| `refresh()` | `invalidate()` (алиас `refresh` до 0.14.0) |

```tsx
const feed = postsProjection.useInfiniteResource(firstPageIds);

// Было
feed.isLoading; feed.isFetchingNext; feed.isError; feed.refresh();

// Стало
feed.isPending; feed.isLoadingNext; feed.hasError; feed.invalidate();
```

Изменилось и содержимое `data`: в него попадают элементы только тех страниц, у которых есть
данные **своих** args (`dataSource: 'current'`), — раньше все страницы с `data !== null`.
Три флага загрузки — не разбиение `isPending`, а «есть хоть одна такая страница»: после
`invalidate()` ленты с упавшей последней страницей `isInvalidating` и `isLoadingNext` истинны
одновременно. Таблица формул — в
[Проекционном ресурсе](../query/usage/projection-resource.md).


## Состояние сцепления команды

У команды нет ни previous, ни смены args, ни плейсхолдера, поэтому набор полей короче:
`status`, `data`, `error`, `args`, `isPending`, `hasData`, `hasError`, метод `retry()`.

| Было | Стало |
|---|---|
| `isLoading` | `isPending` |
| `isSuccess` | `hasData` (⇔ `status === 'success'`) |
| `isError` | `status === 'error'`; `hasError` **шире** — переживает повтор |

```tsx
// Было
const [trigger, { isLoading, isSuccess, isError, error }] = addTodoCommand.useCommand();

// Стало
const [trigger, { isPending, hasData, hasError, error }] = addTodoCommand.useCommand();
```

В `pending` данных больше нет вообще: `data` типизирован строго `null`. Раньше туда могли
просочиться значения прошлого запуска через защитный remap статусов `refreshing` /
`refresh-error`; теперь эти статусы для команды недостижимы — `invalidate()` на записи команды
выводит `console.warn` и ничего не делает. Строки состояния (К1–К5) — в
[API сцепления команды](../query/api/command-clutch.md#варианты-состояния).


## invalidate() на упавшей записи

У записи кэша появился переход `error → pending` с обнулением ошибки, и `invalidate()` его разрешает.
Публичное следствие: **`resource.invalidate(args)` и `entry.invalidate()` на записи в статусе
`error` теперь перезапускают запрос и снимают ошибку**, а в 0.12.3 `refresh()` писал
предупреждение в консоль и ничего не делал.

```typescript
// 0.12.x: no-op + console.warn на упавшей записи
usersResource.refresh({ page: 1 });

// 0.13.0: перезапускает запрос и снимает ошибку
usersResource.invalidate({ page: 1 });

// Нужно сохранить ошибку на экране — это retry, а не инвалидация
usersResource.getEntry({ page: 1 })?.retry();
```

Код, который вызывал `refresh()` вслепую (например, по фокусу окна или по таймеру) и полагался
на то, что упавшая запись останется упавшей, после обновления начнёт её перезапрашивать.

Сцепление при этом продолжает отклонять `invalidate()` там, где показывать нечего (строка 7
матрицы): `console.warn` и no-op. Переход нужен рёбрам «ошибка поверх previous или плейсхолдера
→ перезапрос», которые самой записи не видны. Диаграмма — в
[Состоянии записи запроса](../query/concepts/query-entry-state.md).


## Инвалидация ленивая

`resource.invalidate(args)`, `entry.invalidate()` и связи с `invalidate: true` перезапрашивают
сразу только запись, которую кто-то [удерживает](../query/concepts/cache.md#кто-удерживает-запись):
смонтированный `useResource`, ожидающий `ensure` / `fetch`, `Signal.effect` над `state$`. Запись без
удержаний (компонент размонтирован, запись лежит в retention) только помечается и перезапрашивается
при следующем удержании — подписке или `ensure` / `fetch` / `prefetch`. В 0.12.x запрос уходил всегда.

Код, который полагался на немедленный запрос без подписчиков — прогрев кэша после мутации,
`invalidate()` по таймеру над невидимыми данными, — переходит на `fetch` или
`prefetch(args, { force: true })`:

```typescript
// 0.12.x: запрос уходит сразу, подписчики не нужны
usersResource.refresh({ page: 1 });

// 0.13.0: без подписчиков — только метка, запрос при следующем удержании
usersResource.invalidate({ page: 1 });

// Нужен запрос сейчас
void usersResource.prefetch({ page: 1 }, { force: true });
const fresh = await usersResource.fetch({ page: 1 });
```

Гидрация устаревшего снимка (`snapshotValidTime`, `isStale`, статус `invalidate-error`) по той же
причине больше не стреляет запросами в момент `createApi`: запись рождается в `success` с меткой,
запрос уходит при первом удержании. См. [Снимки](../query/usage/snapshot.md#snapshotvalidtime) и
[правило](../query/concepts/cache.md#инвалидация-тающей-записи).


## invalidate() при запросе в полёте

В 0.12.x `refresh()` на записи с запросом в полёте (`pending` / `refreshing`) писал предупреждение
в консоль и ничего не делал. Теперь `invalidate()` — на ресурсе, записи, сцеплении и через связь —
по умолчанию **прерывает этот запрос и запускает новый** (режим `cancel`): ответ, ушедший до
мутации, не осядет в кэше как свежий. Новый запрос уходит сразу на удерживаемой записи; без
удержаний запрос только прерывается, а новый уходит при следующем удержании — как и вся
[ленивая инвалидация](#инвалидация-ленивая). Код, который полагался на то, что инвалидация поверх
запроса в полёте игнорируется (например, связь с `invalidate: true` на ресурсе, чей запрос
долгий и дорогой), получит лишнее прерывание. Если запрос должен доработать, укажите `trail` —
опцией ресурса `invalidateInFlight: 'trail'`, в вызове `invalidate(args, { inFlight: 'trail' })`
или в связи `invalidate: { inFlight: 'trail' }`; перезапрос тогда уйдёт после его завершения.
Прежнее поведение — ответ текущего запроса принимается, перезапроса нет — даёт `join` (уже без
предупреждения в консоли); ответ, ушедший до мутации, при нём снова осядет как свежий.
Таблица режимов — в [инвалидации в полёте](../query/concepts/cache.md#инвалидация-в-полёте),
поведение стримов — в [стриминговых запросах](../query/usage/stream-query.md#инвалидация-при-открытом-стриме).

**Проекционный ресурс.** Инвалидация набора больше не перезапускает его запуск: стрим записи
остаётся подписанным, а id набора перезагружаются через обёрнутый ресурс по режиму `inFlight` —
опция проекции `invalidateInFlight` (по умолчанию `cancel`) или параметр вызова. Режим
применяется к запросам обёрнутого ресурса, которые летят за id набора: `cancel` — сразу свежий
запрос по всем id, `trail` — после них, `join` — они отвечают за свои id. Следствие:
`onQueryStarted` проекции на инвалидацию больше не срабатывает — сетевые запросы наблюдайте хуками
обёрнутого ресурса. Подробности — в [инвалидации проекции](../query/usage/projection-resource.md#инвалидация).

**Бесконечная лента.** `useInfiniteResource().invalidate()` (в 0.12.x — `refresh()`) пропускала
страницы с запросом в полёте. Теперь она принимает те же опции и инвалидирует каждую страницу, эту
тоже: по умолчанию её запрос прерывается и уходит заново. Прежнее поведение —
`invalidate({ inFlight: 'join' })`.


## fetch() при запросе в полёте

В 0.12.x `fetch(args)` и `prefetch(args, { force: true })` на записи с запросом в полёте дожидались
его результата. Теперь по умолчанию они **прерывают этот запрос и дожидаются нового**
(`inFlight: 'cancel'`): запрос, ушедший до вызова, мог уйти и до мутации, а `fetch` обещает свежий
результат. Режим задаётся в вызове — `fetch(args, { inFlight })`,
`prefetch(args, { force: true, inFlight })` — и **не** берётся из опции ресурса `invalidateInFlight`.

```typescript
// 0.12.x: второй вызов дожидался запроса первого
const a = usersResource.fetch({ page: 1 });
const b = usersResource.fetch({ page: 1 });

// 0.13.0: второй вызов прерывает запрос первого, оба резолвятся результатом нового
const c = usersResource.fetch({ page: 1 });
const d = usersResource.fetch({ page: 1 });

// Прежнее поведение — дождаться запроса в полёте
const e = usersResource.fetch({ page: 1 }, { inFlight: 'join' });
```

Код, который вызывает `fetch` сразу после монтирования `useResource` (или рядом с другим `fetch` /
`prefetch(args, { force: true })` на тех же args), теперь отправит два запроса вместо одного, и
первый будет прерван. Если так и задумано — дедупликация с запросом в полёте, — передайте
`{ inFlight: 'join' }`; `ensure` и `prefetch(args)` без `force` по-прежнему его дожидаются.
`trail` даёт запросу в полёте доработать и резолвится результатом следующего; на открытом стриме
он дожидается завершения стрима. Таблица — в [API ресурса](../query/api/resource.md#запрос-в-полёте-inflight).


## Интерфейсы и типы опций

Обе правки ломают только компиляцию: компилятор укажет на каждое место.

### Собственная реализация ICacheEntry / IQueryCacheEntry

Интерфейсы записи кэша получили новые обязательные члены вместе с
[удержанием записи](../query/concepts/cache.md#кто-удерживает-запись): `ICacheEntry` — `hold()`
и `readonly isMelting`, `IQueryCacheEntry` (расширяет `ICacheEntry`) — ещё и
`readonly isInvalidated`. Класс, который реализует их сам (`implements IQueryCacheEntry<…>`),
должен их добавить. Код, который только читает записи библиотеки, это не затрагивает.

### TResourcePrefetchOptions стал объединением

`TResourcePrefetchOptions` — теперь `TResourcePrefetchCachedOptions | TResourcePrefetchForceOptions`
с дискриминантом `force`, чтобы `inFlight` без `force: true` был ошибкой типов. Интерфейс не может
расширять объединение — расширяйте нужный вариант:

```typescript
// Было
interface IWarmOptions extends TResourcePrefetchOptions { priority: number }

// Стало — вариант с force (или TResourcePrefetchCachedOptions — без него)
interface IWarmOptions extends TResourcePrefetchForceOptions { priority: number }

// Или пересечение, если нужны оба варианта
type TWarmOptions = TResourcePrefetchOptions & { priority: number };
```


## Снимки: версия 2

`CURRENT_SNAPSHOT_VERSION` поднят до `2`: в снимке статус записи хранится строкой, а строки
переименованы.

| Направление | Поведение |
|---|---|
| 0.13.0 читает снимок версии 1 | `refreshing` / `refresh-error` трактуются как `invalidating` / `invalidate-error` |
| 0.12.x читает снимок версии 2 | записи с `invalidate-error` не гидрируются — такой статус ей незнаком |

Для SSR это значит: клиент и сервер обновляются вместе. Смешанный деплой, где старый клиент
читает снимок нового сервера, теряет часть записей (они просто загрузятся заново).
См. [Снимки](../query/usage/snapshot.md).


## Redux DevTools

Имена действий переименованы вместе со статусами записи. Изменилось и само значение, которое
уходит в дерево: теперь это плоская запись состояния, а не сериализованный экземпляр `Machine`
с полем `state` внутри — см. [beforeDevtoolsPush](#beforedevtoolspush-получает-плоскую-запись).

| Было | Стало |
|---|---|
| `UPDATE: refresh` | `UPDATE: invalidate` |
| `UPDATE: refresh-error` | `UPDATE: invalidate-error` |

Фильтры и записанные сессии devtools под старыми именами перестанут совпадать. Полная таблица —
в [Devtools](../devtools/README.md#имена-действий-у-ресурсов-и-команд).


## LocalSignal: zodSchema → schema

Опция принимает любую [Standard Schema](https://standardschema.dev), а не только Zod, и `zod`
ушёл из `peerDependencies`. Алиаса нет — компилятор укажет каждое место.

```typescript
// 0.12.x
LocalSignal.state({ key: 'filter', defaultValue: FILTER.ALL, zodSchema: z.enum(FILTER) });

// 0.13.0 — та же схема Zod, другое имя опции
LocalSignal.state({ key: 'filter', defaultValue: FILTER.ALL, schema: z.enum(FILTER) });
```

Схема должна быть синхронной: у асинхронной (например, с `.refine(async …)` в Zod) значение из
хранилища игнорируется, в консоль уходит `console.error`. Если `zod` нужен только для этой
опции и больше нигде, его можно удалить из зависимостей приложения.


## Удалены deprecated из 0.11.1

Объявлены устаревшими в 0.11.1 ([гайд 0.11.0](./0.11.0.md)) и удалены в этом релизе. Компилятор укажет каждое место вызова.

| Что | Замена |
|---|---|
| `command.trigger(args, entryKey?)` (уровень ядра) | `command.execute(args, entryKey?)` — контракт идентичен |
| `resource.trigger(args)` | `resource.prefetch(args)` |
| `resource.trigger(args, true)` | `resource.prefetch(args, { force: true })` |
| `signalize(obs)` | `Signal.from(obs)` |
| `signalize(obs, defaultValue)` | `Signal.from(obs, { default: defaultValue })` |

`clutch.trigger()` у сцепления команды и `trigger` из `useCommand` не затронуты.

`prefetch` — не точная замена `resource.trigger`. Каждый вызов `prefetch` — включая попадания
в кэш — [удерживает](../query/concepts/cache.md#кто-удерживает-запись) запись до резолва и затем
перезапускает отсчёт `retentionTime`, а на записи в состоянии `error` делает ретрай (ошибка
остаётся читаемой). С `force: true` он запрашивает сразу, даже запись без удержаний, а запрос в
полёте обрабатывает по своему `inFlight` (по умолчанию `cancel`), а не по опции ресурса
`invalidateInFlight`. Без удержания и ретрая:

```typescript
// trigger(args) — синхронно создать и запустить запись, не трогая удержание
resource.getEntry(args, true);

// trigger(args, true) — то же, а существующую запись инвалидировать
resource.invalidate(args);
resource.getEntry(args, true);
```

Инвалидация в 0.13.0 [ленивая](#инвалидация-ленивая): запись без удержаний `invalidate` только
помечает — запрос уйдёт при следующем удержании, — а упавшую перезапрашивает, сняв ошибку
(см. [`invalidate()` на упавшей записи](#invalidate-на-упавшей-записи)). Нужен запрос сейчас —
`prefetch(args, { force: true })`.

`signalize` переподписывался на источник при каждом чтении. `Signal.from` по умолчанию удерживает
подписку (`keepAlive: 'microtask'`) и отдаёт горячие чтения из кэша. Точный эквивалент старого
поведения — `Signal.from(obs, { keepAlive: 'none' })`, см.
[Signal.from](../signals/README.md#signalfrom). В отличие от `signalize`, `Signal.from` возвращает
`DisposableSignal` — долгоживущий сигнал стоит освобождать через `dispose()`.


## Что не изменилось

- `Resource`, `Command`, `queryFn`, `SKIP`, `mapError`.
- `command.execute`.
- Прежние вызовы компилируются как есть, но поведение изменилось: `links` и `invalidate: true`
  ([инвалидация ленивая](#инвалидация-ленивая),
  [в полёте](#invalidate-при-запросе-в-полёте)), `ensure` / `fetch` / `prefetch`
  ([`fetch()` при запросе в полёте](#fetch-при-запросе-в-полёте)),
  `unstable_createProjectionResource` ([инвалидация проекции](#invalidate-при-запросе-в-полёте)).
  `retentionTime` со статическим значением работает как прежде; функция — новая форма, см.
  [время удержания записи](../query/concepts/cache.md#время-удержания-записи).
- `clutch.start()`, `clutch.adoptPrevious()`, `clutch.retry()`, `clutch.whenSettled()`,
  `clutch.trigger()` — имена и контракты прежние. Условие резолва `whenSettled` то же самое:
  есть что отрисовать либо запрос упал, не оставив ничего на экране.
- Конверт результата `trigger` (`TTriggerResult` / `TTriggerPromise`, `unwrap()`), `wrapTrigger`.
- Опция команды `key` и `requestId`.
- Вызов `resource.getState(args)` — изменился только тип результата.
- `isSwitching` — имя и формула. `isInitialLoading` сохранил имя; формула учла плейсхолдер.

## Удалено без алиасов

Алиас на изменившуюся форму был бы ложью, поэтому его нет.

- Флаги состояния сцепления ресурса и записи: `isLoading`, `isRefreshing`, `isRefreshError`,
  `isRetrying`, `isSuccess`, `isError`.
- Флаги `useInfiniteResource`: `isLoading`, `isFetchingNext`, `isError`.
- Флаги состояния команды: `isLoading`, `isSuccess`, `isError`.
- Статусы `'refreshing'` / `'refresh-error'` — переименованы у записи кэша и полностью убраны из
  состояния сцепления и `getState()`.
- Поле `isRetrying` в состояниях записи `TQueryEntryPendingState` / `TQueryEntryInvalidatingState`:
  повтор в полёте определяется по `error !== null`.
- Обёртка `.state` у `entry.state$()` / `entry.peek()` / `entry.set()` — состояние стало плоским,
  см. [Состояние записи кэша](#состояние-записи-кэша).
- Свойство `entry.machine$` — состояние записи отдаёт `entry.state$`, плоской записью.
- Классы `Machine`, `MachineBase`, `MachineWithData`, `MachinePending`, `MachineSuccess`,
  `MachineError`, `MachineInvalidating`, `MachineInvalidateError` — больше не экспортируются
  из пакета: это внутренняя алгебра переходов.
- Опция записи кэша `initialMachine` — вместо неё `initialState` с плоской записью.
- Опция `LocalSignal.state({ zodSchema })` — вместо неё `schema`, см.
  [LocalSignal: zodSchema → schema](#localsignal-zodschema--schema).
- Типы `TRetrying`, `TSuspenseResourceErrorState`, а также варианты состояния, описывавшие
  статусы `refreshing` / `refresh-error`: `TResourceAgentRefreshingState`,
  `TResourceAgentRefreshErrorState`, `TResourceLiteRefreshingState`,
  `TResourceLiteRefreshErrorState` — вместе с формами, которые они описывали. Их строки
  матрицы теперь покрывают `TResourceClutchPendingCurrentState` и `TResourceClutchErrorState`.
- Типы `TRefreshingState` / `TRefreshErrorState` — переименованы в
  `TQueryEntryInvalidatingState` / `TQueryEntryInvalidateErrorState`, см.
  [refresh → invalidate](#refresh--invalidate).
