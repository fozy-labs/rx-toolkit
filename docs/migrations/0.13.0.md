# Миграция с версии 0.12.x на 0.13.0

В модуле Query переименован словарь — старые имена остались `@deprecated`-алиасами до 0.14.0.
Без алиасов изменились форма состояния сцепления и состояние записи кэша, иначе ведут себя
инвалидация и `fetch`. В сигналах переписаны ядро и обработка ошибок.

## Порядок миграции

1. Обновиться, собрать проект и исправить [то, что покажет компилятор](#что-покажет-компилятор).
2. Пройти [изменения поведения](#изменения-поведения): этот код компилируется, но работает иначе.
3. Переименовать API по [словарю](#словарь) — алиасы работают до 0.14.0.


## Изменения поведения

Компилятор на эти места не укажет.

### Статус error стал шире

`status: 'error'` теперь покрывает и провал инвалидации поверх данных — в 0.12.x у него был свой
статус `'refresh-error'`. Код, который читал `status === 'error'` как «показать нечего», начнёт
заменять готовые данные панелью ошибки. Различает эти случаи `hasData`:

```tsx
// Было
if (state.status === 'refresh-error') return <StaleBanner data={state.data} error={state.error} />;
if (state.status === 'error') return <ErrorPanel error={state.error} />;

// Стало
if (state.status === 'error' && state.hasData) return <StaleBanner data={state.data} error={state.error} />;
if (state.status === 'error') return <ErrorPanel error={state.error} />;
```

### switch (status) больше не разбиение

Инвалидация текущих args — это `status: 'pending'` при свежих данных на экране (в 0.12.x —
`'refreshing'`). `switch (status)` без проверки `hasData` покажет спиннер на каждой инвалидации.
Проверяйте по порядку: есть что показать → ошибка → загрузка.

```tsx
// Было
switch (state.status) {
    case 'pending': return <Spinner />;
    case 'refreshing': return <List items={state.data} stale />;
    case 'success': return <List items={state.data} />;
    case 'refresh-error':
    case 'error': return <ErrorPanel error={state.error} />;
    case 'idle': return null;
}

// Стало
if (state.hasData) return <List items={state.data} stale={state.isPending} error={state.error} />;
if (state.hasError) return <ErrorPanel error={state.error} retrying={state.isPending} onRetry={state.retry} />;
if (state.isPending) return <Spinner />;
return null; // idle
```

`state.hasData` сужает `data` до `TData` без `| null`, `state.hasError` — `error` до `TError`.

### hasData вместо проверки data

`TData` сам может быть `null` (например, `queryFn` отдаёт `null` на «ничего не найдено»). Свежие
данные `null` дают `hasData: true`, поэтому `data !== null` и `data &&` отправят такой экран
в загрузку или в ошибку.

```tsx
// Было
if (query.data) { /* … */ }

// Стало
if (query.hasData) { /* … */ }
```

### useSuspenseResource

Хук возвращает состояние, если есть что показать (`hasData`); бросает ошибку в Error Boundary,
если показать нечего; иначе приостанавливает рендер. Ошибка поверх данных предыдущих args или
плейсхолдера теперь возвращается в состоянии — в 0.12.x при `data === null` она долетала до
Error Boundary. Читайте `hasError`.

```tsx
// Было
const { data, isRefreshing, isRefreshError } = userResource.useSuspenseResource({ id });

// Стало
const { data, isInvalidating, hasError } = userResource.useSuspenseResource({ id });
```

Подробности — в [React-хуках](../usage/react/README.md#usesuspenseresource).

### Дескриптор команды: key → entryKey

У дескриптора из `command.bind()` поле `key` стало `entryKey`, а алиас `TPackedCommand` указывает
на новый тип. В типизированном коде компилятор укажет на чтение `.key`. За нетипизированной
границей — JS, `any`, собственный реестр, транспорт — `.key` молча даёт `undefined`, и команда
запускается со сгенерированным ключом вместо общего. Найдите чтения поля грепом.

```typescript
// Было
const { key } = addTodoCommand.pack({ text: 'Задача' }, 'my-key');

// Стало
const { entryKey } = addTodoCommand.bind({ text: 'Задача' }, 'my-key');
```

### Чтение .state у записи кэша

Состояние записи кэша стало плоским: `entry.state$().status` вместо `entry.state$().state.status`.
За нетипизированной границей (JS, `any`, собственный логгер, сериализация записи) `.state`
молча даёт `undefined`. Найдите `.state$().state` и `.peek().state` грепом. Остальные изменения —
в [Состоянии записи кэша](#состояние-записи-кэша).

### invalidate() на упавшей записи

`resource.invalidate(args)` и `entry.invalidate()` на записи в `error` перезапускают запрос и
снимают ошибку; `refresh()` в 0.12.x писал предупреждение и ничего не делал. Код, который вызывал
`refresh()` вслепую — по фокусу окна, по таймеру, — начнёт перезапрашивать упавшие записи.
Сцепление, которому нечего показать, по-прежнему отвечает на `invalidate()` `console.warn`.

```typescript
// Перезапрос со снятием ошибки
usersResource.invalidate({ page: 1 });

// Перезапрос с ошибкой на экране
usersResource.getEntry({ page: 1 })?.retry();
```

### Инвалидация ленивая

`resource.invalidate(args)`, `entry.invalidate()` и связи с `invalidate: true` перезапрашивают
сразу только запись, которую кто-то [удерживает](../query/concepts/cache.md#кто-удерживает-запись):
смонтированный `useResource`, ожидающий `ensure` / `fetch`. Запись без удержаний только
помечается и перезапрашивается при следующем удержании. В 0.12.x запрос уходил всегда.

Прогрев кэша после мутации и `invalidate()` по таймеру над невидимыми данными переходят на
`fetch` или `prefetch(args, { force: true })`:

```typescript
// Без подписчиков — только метка
usersResource.invalidate({ page: 1 });

// Запрос сейчас
void usersResource.prefetch({ page: 1 }, { force: true });
const fresh = await usersResource.fetch({ page: 1 });
```

По той же причине устаревший снимок (`snapshotValidTime`, `isStale`, `invalidate-error`) больше
не отправляет запросы в момент `createApi`: запрос уходит при первом удержании записи. См.
[Снимки](../query/usage/snapshot.md#snapshotvalidtime).

### invalidate() при запросе в полёте

В 0.12.x `refresh()` на записи с запросом в полёте писал предупреждение и ничего не делал.
Теперь `invalidate()` по умолчанию прерывает этот запрос и отправляет новый (режим `cancel`),
чтобы ответ, ушедший до мутации, не осел в кэше как свежий.

- Долгий дорогой запрос должен доработать — режим `trail`: перезапрос уйдёт после него.
- Прежнее поведение без предупреждения — режим `join`.

Режим задаётся опцией ресурса `invalidateInFlight`, в вызове `invalidate(args, { inFlight })` или
в связи `invalidate: { inFlight }`. Таблица режимов — в
[инвалидации в полёте](../query/concepts/cache.md#инвалидация-в-полёте), стримы — в
[стриминговых запросах](../query/usage/stream-query.md#инвалидация-при-открытом-стриме).

**Проекционный ресурс.** Инвалидация набора больше не перезапускает его запуск: id набора
перезагружаются через обёрнутый ресурс по тому же режиму. `onQueryStarted` проекции на
инвалидацию не срабатывает — сетевые запросы видны хукам обёрнутого ресурса. См.
[инвалидацию проекции](../query/usage/projection-resource.md#инвалидация).

**Бесконечная лента.** `useInfiniteResource().invalidate()` больше не пропускает страницы с
запросом в полёте. Прежнее поведение — `invalidate({ inFlight: 'join' })`.

### fetch() при запросе в полёте

`fetch(args)` и `prefetch(args, { force: true })` на записи с запросом в полёте прерывают его и
дожидаются нового; в 0.12.x они дожидались текущего. Режим задаётся только в вызове, опция
ресурса `invalidateInFlight` на него не влияет.

```typescript
// 0.12.x: второй вызов дожидался запроса первого
// 0.13.0: второй вызов прерывает запрос первого, оба резолвятся результатом нового
const a = usersResource.fetch({ page: 1 });
const b = usersResource.fetch({ page: 1 });

// Дождаться запроса в полёте, как в 0.12.x
const c = usersResource.fetch({ page: 1 }, { inFlight: 'join' });
```

`fetch` сразу после монтирования `useResource` или рядом с другим `fetch` на тех же args теперь
отправляет второй запрос и прерывает первый. Если нужна дедупликация — `{ inFlight: 'join' }`;
`ensure` и `prefetch(args)` без `force` по-прежнему дожидаются запроса в полёте. Таблица режимов —
в [API ресурса](../query/api/resource.md#запрос-в-полёте-inflight).

### Ошибки в сигналах

Исключение из пользовательского кода больше не выключает часть графа.

| Что бросило | 0.12.x | 0.13.0 |
|---|---|---|
| `computeFn` computed с подписчиками | Ошибка вылетала из `set()`, computed замирал на последнем удачном значении | Ошибка — состояние computed: чтения бросают её, пока не изменится зависимость. Подписчик `obs` получает `error` |
| `effectFn` на повторном запуске | Эффект отписывался навсегда | Эффект жив и перезапустится; ошибка — из `set()` |
| Реакция во время батча | Остальные реакции отбрасывались | Выполняются все, затем пробрасывается первая ошибка |
| Сигнал в `useSignal` | Необработанная RxJS-ошибка, компонент застывал | Ошибка уходит в ближайший `ErrorBoundary` |

Что проверить: `try/catch` вокруг `set()`, ловивший ошибку computed, — теперь её ловят при чтении
или в `ErrorBoundary`; упавший эффект, который не должен перезапускаться, отписывайте явно.

### Ядро сигналов

| Что | 0.12.x | 0.13.0 |
|---|---|---|
| `.obs` у `Signal.from` и `SourceSignal.create` | Каждое значение источника сразу | Одно значение за батч; синхронная серия при подключении — тоже одно (`of(1, 2, 3)` отдаёт `3`). `State.obs` отдаёт каждую запись сразу, как и раньше |
| Producer `SourceSignal.create` | Запускался на каждого подписчика `.obs` и на каждое чтение | Один на всех наблюдателей, пока есть хоть один |
| Порядок независимых эффектов | По глубине графа | В порядке постановки в очередь |
| Ошибка в цепочке `Signal.from(a.obs.pipe(…))` | Следующее чтение переподписывало цепочку | Ошибка держится, пока не изменится `a` |
| Петля через эффекты, `.obs` или [мосты](../signals/README.md#мосты-через-rxjs) | Зависание внутри `set()` | `SignalCycleError` из записи или `Batcher.run` |

Что проверить: код, полагавшийся на порядок эффектов, — упорядочьте их через данные; producer
`SourceSignal.create` с побочным эффектом на каждого подписчика; подписчиков `.obs` у
`Signal.from`, считавших эмиссии внутри батча. Подробности — в [RxSignals](../signals/README.md#интеграция-с-rxjs).

### Redux DevTools

Действия переименованы вместе со статусами записи, а значением в дереве стала
[плоская запись состояния](#состояние-записи-кэша). Фильтры и записанные сессии под старыми
именами перестанут совпадать.

| Было | Стало |
|---|---|
| `UPDATE: refresh` | `UPDATE: invalidate` |
| `UPDATE: refresh-error` | `UPDATE: invalidate-error` |

Полная таблица — в [Devtools](../devtools/README.md#имена-действий-у-ресурсов-и-команд).

### Снимки: версия 2

| Направление | Поведение |
|---|---|
| 0.13.0 читает снимок версии 1 | `refreshing` / `refresh-error` читаются как `invalidating` / `invalidate-error` |
| 0.12.x читает снимок версии 2 | записи с `invalidate-error` не гидрируются |

Обновляйте клиент и сервер SSR вместе: при смешанном деплое старый клиент теряет часть записей
из снимка нового сервера, и они загружаются заново. См. [Снимки](../query/usage/snapshot.md).


## Что покажет компилятор

### Состояние сцепления ресурса

`status` отвечает только на вопрос «идёт ли запрос и чем кончился прошлый»:
`'idle' | 'pending' | 'success' | 'error'`. Что показано на экране, говорит `dataSource`:
`'none' | 'placeholder' | 'previous' | 'current'`. Все варианты и переходы — в
[API сцепления ресурса](../query/api/resource-clutch.md#варианты-состояния).

| Было (0.12.x) | Стало (0.13.0) | Примечание |
|---|---|---|
| `isLoading` | `isPending` | точный эквивалент |
| `isRefreshing` | `isInvalidating \|\| isSwitching` | только фоновое обновление текущих args — `isInvalidating` |
| `isRefreshError` | `status === 'error' && dataSource === 'current'` | |
| `isRetrying` | `isPending && hasError` | |
| `isSuccess` | `status === 'success'` | для рендера данных нужен `hasData` |
| `isError` | `status === 'error'` | `hasError` шире: он истинен и во время повтора |
| `status === 'refreshing'` | `isPending && hasData` | только для текущих args — `isInvalidating` |
| `status === 'refresh-error'` | `status === 'error' && dataSource === 'current'` | |
| `data !== null` | `hasData` | см. [hasData вместо проверки data](#hasdata-вместо-проверки-data) |

`isSwitching` не изменился; `isInitialLoading` сохранил имя, но истинен и при загрузке под
плейсхолдером.

`resource.getState(args)` возвращает тот же набор полей и флагов с `dataSource`, суженным до
`'none' | 'current'`, без методов. Его тип `IResourceLiteState` стал `TResourceEntryState`, варианты —
`TResourceEntry{Idle,Pending,Success,Error}State`.

### useInfiniteResource

| Было | Стало |
|---|---|
| `isLoading` | `isPending` |
| `isFetchingNext` | `isLoadingNext` |
| `isError` | `hasError` |
| — | `isInvalidating`, `hasData` |

В `data` теперь попадают элементы только тех страниц, у которых есть данные своих args
(`dataSource: 'current'`), — раньше все страницы с `data !== null`. Формулы флагов — в
[Проекционном ресурсе](../query/usage/projection-resource.md#бесконечная-лента-useinfiniteresource).

### Состояние сцепления команды

| Было | Стало |
|---|---|
| `isLoading` | `isPending` |
| `isSuccess` | `hasData` |
| `isError` | `status === 'error'`; `hasError` шире — истинен и во время повтора |

```tsx
// Было
const [trigger, { isLoading, isSuccess, isError, error }] = addTodoCommand.useCommand();

// Стало
const [trigger, { isPending, hasData, hasError, error }] = addTodoCommand.useCommand();
```

В `pending` `data` типизирован как `null`. Варианты — в
[API сцепления команды](../query/api/command-clutch.md#варианты-состояния).

### Состояние записи кэша

Запись больше не завёрнута в публичный класс `Machine`: `entry.state$()`, `entry.peek()` и
`entry.set()` работают с плоским `TQueryEntryState<TArgs, TData>`.

| Было | Стало |
|---|---|
| `entry.state$().state.status` | `entry.state$().status` |
| `entry.machine$()` | `entry.state$()` |
| `entry.machine$() instanceof MachineSuccess` | `entry.state$().status === 'success'` |
| `initialMachine: Machine.fromSnapshot({ args, data, updatedAt })` | `initialState: { status: 'success', args, data, error: null, updatedAt, patchState: null }` |
| `beforeDevtoolsPush: (machine, push) => …machine.state.status` | `beforeDevtoolsPush: (state, push) => …state.status` |
| статусы `'refreshing'` / `'refresh-error'` | `'invalidating'` / `'invalidate-error'` |

- Вызовы переходов машины (`machine.success(data)`, `machine.fail(error)` и т. п.) заменяются
  публичными входами `entry.invalidate()`, `entry.retry()`, `entry.createPatch()`.
- `initialState` подавляет автоматический первый запуск. Устаревший снимок передаётся опцией
  `isInvalidated: true` при `success`, а не статусом `invalidating`.
- Поля `isRetrying` в `pending` / `invalidating` больше нет: повтор в полёте — `error !== null`.

Модель целиком — в [Состоянии записи запроса](../query/concepts/query-entry-state.md).

### Интерфейсы и типы опций

**Собственная реализация `ICacheEntry` / `IQueryCacheEntry`** должна добавить `hold()` и
`readonly isMelting`, а для `IQueryCacheEntry` — ещё `readonly isInvalidated`. См.
[удержание записи](../query/concepts/cache.md#кто-удерживает-запись).

**`TResourcePrefetchOptions` стал объединением** `TResourcePrefetchCachedOptions |
TResourcePrefetchForceOptions`, и интерфейс больше не может его расширять:

```typescript
// Было
interface IWarmOptions extends TResourcePrefetchOptions { priority: number }

// Стало — нужный вариант или пересечение
interface IWarmOptions extends TResourcePrefetchForceOptions { priority: number }
type TWarmOptions = TResourcePrefetchOptions & { priority: number };
```

### LocalSignal: zodSchema → schema

Опция принимает любую синхронную [Standard Schema](https://standardschema.dev); `zod` больше не
peer-зависимость. Схемы Zod передаются как есть.

```typescript
// Было
LocalSignal.state({ key: 'filter', defaultValue: FILTER.ALL, zodSchema: z.enum(FILTER) });

// Стало
LocalSignal.state({ key: 'filter', defaultValue: FILTER.ALL, schema: z.enum(FILTER) });
```

С асинхронной схемой (например, `.refine(async …)` в Zod) значение из хранилища игнорируется,
а в консоль уходит `console.error`.

### Signal.effect: teardown или ничего

`effectFn` должен вернуть teardown или ничего, как у `Effect.create`. Стрелка-выражение,
возвращающая значение, теперь ошибка типов.

```typescript
// Было
Signal.effect(() => values.push(count()));

// Стало
Signal.effect(() => {
    values.push(count());
});
```

### Удалены deprecated из 0.11.1

| Что | Замена |
|---|---|
| `command.trigger(args, entryKey?)` (уровень ядра) | `command.execute(args, entryKey?)` — контракт тот же |
| `resource.trigger(args)` | `resource.prefetch(args)` |
| `resource.trigger(args, true)` | `resource.prefetch(args, { force: true })` |
| `signalize(obs)` | `Signal.from(obs)` |
| `signalize(obs, defaultValue)` | `Signal.from(obs, { default: defaultValue })` |

`clutch.trigger()` и `trigger` из `useCommand` не затронуты.

`prefetch` удерживает запись до резолва, перезапускает отсчёт `retentionTime` и делает ретрай
упавшей записи. Без этого `trigger(args)` заменяет `resource.getEntry(args, true)`, а
`trigger(args, true)` — `resource.invalidate(args)` перед ним; но инвалидация теперь
[ленивая](#инвалидация-ленивая).

`Signal.from` держит подписку на источник и отдаёт чтения из кэша. Ближе всего к `signalize` —
`Signal.from(obs, { keepAlive: 'none' })`, но и он не точный эквивалент: `signalize` подписывался на
источник заново при каждом чтении и давал каждому подписчику `.obs` свою подписку, а `Signal.from` так
подписывается только на чтение без наблюдателей — пока они есть, все делят одну подписку и её кэш.
Проверьте код, которому нужна своя подписка на холодный источник. Долгоживущий сигнал освобождайте через
`dispose()`. См. [Signal.from](../signals/README.md#signalfrom).


## Словарь

Старые имена — `@deprecated`-алиасы, удаляются в 0.14.0. Семантика вызовов та же, кроме
перечисленного в [изменениях поведения](#изменения-поведения).

| Было | Стало |
|---|---|
| `resource.createAgent()` | `resource.createClutch()` |
| `command.createAgent(key?)` | `command.createClutch(entryKey?)` |
| `IResourceAgent`, `ICommandAgent` | `IResourceClutch`, `ICommandClutch` |
| `TAgentStatus` | `TClutchStatus` |
| `resource.refresh(args)`, `entry.refresh()`, `clutch.refresh()`, `state.refresh()` | `invalidate` с теми же аргументами |
| `useInfiniteResource(...).refresh()` | `useInfiniteResource(...).invalidate()` |
| `clutch.set(args)`, `clutch.set(args, true)` | `clutch.switch(args)`, `clutch.switch(args, { markPending: true })` |
| `clutch.setKey(key)` | `clutch.setEntryKey(entryKey)` |
| `resource.pack(args)` | `resource.bind(args)` |
| `command.pack(args, key?)` | `command.bind(args, entryKey?)` |
| `TPackedResource`, `TPackedCommand`, `TPacked` | `TBoundResource`, `TBoundCommand`, `TBound` |
| `Args`, `ArgsOrVoid`, `ArgsOrVoidOrSkip`, `Keyed` | `TArgsOrKeyed`, `TArgsOrVoid`, `TArgsOrVoidOrSkip`, `TKeyed` |
| `PluginHKT`, `ReactHooksPluginHKT` | `IPluginHKT`, `IReactHooksPluginHKT` |
| `CombinePlugin*Augments` | `TCombinePlugin*Augments` |
| `TMachineState`, `TMachineStatus` | `TQueryEntryState`, `TQueryEntryStatus` |
| `TPendingState`, `TSuccessState`, `TErrorState`, `TInvalidatingState`, `TInvalidateErrorState` | `TQueryEntry{Pending,Success,Error,Invalidating,InvalidateError}State` |
| `composeHooks(a, b)` | массив в опции: `onQueryStarted: [a, isDev && b]` |

- `TAgentStatus` сузился до четырёх значений `TClutchStatus`: код, перечисляющий
  `'refreshing'` / `'refresh-error'`, алиас не спасёт.
- Параметр `key` переименован в `entryKey` у `execute`, `createClutch`, `bind`, `trigger` и
  `useCommand` — позиция та же. Опция команды `key` и `requestId` не изменились. Поле
  дескриптора `.key` алиаса не имеет, см. [Дескриптор команды](#дескриптор-команды-key--entrykey).
- Алиасы `TMachineState` и семейства сохраняют имя, но не поле `isRetrying`.
- Массив хуков пропускает falsy-элементы; семантика та же, что у `composeHooks`. См.
  [Lifecycle-хуки](../query/usage/lifecycle.md).


## Удалено без алиасов

- Флаги и статусы старого состояния сцепления, `getState()`, команды и `useInfiniteResource` —
  замены в [Что покажет компилятор](#что-покажет-компилятор).
- Типы `TResourceAgentState` / `TCommandAgentState` — теперь `TResourceClutchState` /
  `TCommandClutchState`; `IResourceLiteState` и варианты — `TResourceEntryState`; `TRetrying`,
  `TSuspenseResourceErrorState` и варианты для статусов `refreshing` / `refresh-error`.
- Типы `TRefreshingState` / `TRefreshErrorState` — теперь `TQueryEntryInvalidatingState` /
  `TQueryEntryInvalidateErrorState`.
- Обёртка `.state`, `entry.machine$`, классы `Machine*` и опция `initialMachine` — см.
  [Состояние записи кэша](#состояние-записи-кэша).
- Опция `LocalSignal.state({ zodSchema })` — см. [LocalSignal](#localsignal-zodschema--schema).
- Внутренности движка сигналов: `DependencyTracker`, `DependencyRecord`, `ComputeCache`,
  `SyncObservable`, `Batcher.scheduler`, protected `State.bs$` и `SourceSignal.rang`,
  `Effect._getRang()`, `.value` у `obs` класса `SourceSignal`. Замены нет; синхронное чтение
  Observable с default, для которого служил `SyncObservable`, —
  `SourceSignal.create(subscribe, defaultValue).peek()`.
